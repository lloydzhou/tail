# Tail 传输层:协议与数据管线

> 本文描述**当前实现**的完整协议与管线,所有常量、字节布局、行为均与代码逐项核对。
> 代码位置:`tail/transport/`。
>
> 审核要点集中在每节的「设计依据」——每一个决策都应能指向一个行业参考实现
> (vLLM / DeepSeek / OpenAI / Borg)或一组实测数据,没有自创机制。

---

## 1. 它解决什么问题

客户端 SDK 与推理服务之间的请求体是 OpenAI Chat Completions 的 JSON。多轮对话里,
每一轮都要把**整份历史**重新上传一次,其中绝大部分与上一轮完全相同。

目标:

1. **减少公网传输字节**——重复的前缀不再传。
2. **不改变上游协议**——推理服务收到的是**标准** OpenAI JSON,它完全不需要知道 Tail 存在。

Tail 插在中间:

```
客户端 SDK
   │  ① 渲染:JSON → 一维文本(固定顺序,确定性)
   │  ② 自检:对到「服务端已有」的前缀边界 L,只留尾部
   ▼
 ══════ 公网 ══════   ③ 只传 L 之后的字节(通常只有新增的那一段)
   ▼
 网关
   │  ④ 切块 + 父链哈希(哈希的唯一权威),按 (L, H) 走链取前缀
   │  ⑤ 反渲染:文本 → 标准 OpenAI JSON
   ▼
推理服务(DeepSeek / vLLM / ...)   ⑥ 收到的就是普通 JSON
```

**为什么先把 JSON 变成文本**:JSON 是树,块边界没有自然落点;摊平成一维字节流后
才能按固定间隔切块并跨轮复用。这一层还顺手省掉每条消息的 `{"role":"`,
`","content":"` 这类零信息结构字节。

## 2. 分层与不变式

| 层 | 模块 | 输入 → 输出 | 懂 LLM 语义 |
|---|---|---|---|
| 渲染器 | `render.py` | messages JSON → 一维文本 | ✅ |
| 前缀客户端 | `codec.PrefixClient` | 文本 + 凭据 → 尾部字节流 | ❌ 只认字节 |
| 前缀读取器 | `codec.PrefixReader` | 前缀 + 尾部字节 → 完整文本流(切块/哈希在这里) | ❌ 只认字节 |
| 反渲染器 | `render.py` | 一维文本 → messages JSON | ✅ |
| 分块/哈希 | `chunking.py` | 字节 → 块 + 块哈希 | ❌ 只认字节 |
| 链式存储 | `storage.py` | 链尾 + 块数 → 块哈希列表 / 块内容 | ❌ 只认字节 |

三条不变式:

1. **渲染必须确定性**——同一份 messages 必须渲染成**逐字节相同**的文本,否则块内容
   变化、`block_hash` 变化、缓存整体失效。实现手段:`sort_keys=True` 的 JSON 序列化、
   固定的顶层参数顺序。
2. **中间层无语义**——前缀客户端/读取器不知道哪个字节是 role。要支持 Anthropic Messages
   或 Responses API,只需写新的 `render` 模块,中间两层一行不改。
3. **缓存缺失只退化,不报错**——前缀不完整时**立刻中止**这次上游请求(HTTP 409 +
   `X-Tail-Retransmit: 1`),客户端丢掉该会话凭据后重发全文。存储全空、服务重启时
   系统仍能正常工作。**不允许「跳过缺块继续解」**:见 §8。

## 3. 渲染格式

### 3.1 标记集合

包装语法 `<|name|>` 取自 **OpenAI Harmony** 的 formatting token
(`<|start|>` / `<|message|>` / `<|end|>`)。名字本身**没有一个是我发明的**:

- **role 标记**:`<|system|>` `<|user|>` `<|assistant|>` `<|tool|>` `<|developer|>`
  `<|function|>` —— 就是 OpenAI 的 `role` 取值原文。
- **字段标记**:`<|tool_calls|>` `<|tool_call_id|>` `<|name|>` `<|extra|>` ——
  `tool_calls` / `tool_call_id` / `name` 是 OpenAI 字段名原文;`extra` 见 §3.5。
- **顶层参数标记**:`<|model|>` `<|temperature|>` 等 21 个,全部是 OpenAI
  请求体字段名原文(顺序固定,见 `render.PARAM_ORDER`)。

### 3.2 布局

```
<|model|>"deepseek-chat"<|temperature|>0.7<|system|>"你是助手。"<|user|>"你好"
```

规则:

1. 顶层参数在前,顺序由 `PARAM_ORDER` 固定(确定性要求)。
2. 参数值用 `json.dumps(sort_keys=True)` 序列化。
3. 每个 message 以 role 标记开头,正文是 **JSON 字符串**(不是裸文本)。
4. message 内部字段以 `<|字段名|>` 引出,值同样是 JSON 字符串。
5. **格式版本不进正文**,走 HTTP 头 `X-Tail-Version`。写进正文会让版本号落在第一个块上,
   升版即全量失效。

### 3.3 正文为什么必须是 JSON 字符串

这是为了消除歧义,不是风格选择。若正文裸输出,用户在 prompt 里写一句
"请把 `<|user|>` 当作分隔符"就会**把整条流解析错位**(实测直接抛
`JSONDecodeError`)。

改用 JSON 字符串承载后,正文里的标记由 JSON 的字符串/转义语义保护,解析器只需
跟踪"当前是否在 JSON 字符串内部",在字符串内部出现的 `<|` 不算结构。
**没有引入任何新的转义符号**——用的就是 JSON 自己的引号与反斜杠。

代价实测:纯中文约 **0.6%**,含大量引号/换行的代码约 **13~19%**。

### 3.4 tool_calls

按 OpenAI 原结构做确定性 JSON,**不发明** `name(args)` 之类的语法:

```
<|assistant|><|tool_calls|>[{"function":{"arguments":"{\"city\": \"北京\"}","name":"get_weather"},"id":"c1","type":"function"}]
```

`arguments` 按**原字符串**保留(不重新序列化)——重新序列化会改变空白
(`{"k": 1}` → `{"k":1}`),字节就不一致了。

> 曾经用 `name(args)` 这种"函数调用"写法,有两个真实缺陷:`id`/`type` 字段无处安放
> 直接丢失;assistant 正文里出现 `f({"a":1})` 时会被误判成 tool_call。

### 3.5 `content` 的三种形态

OpenAI 里 `content: null`、`content` 缺失、`content: ""` 是三种不同语义,但它们
都不产生正文,纯看字节流无法区分。用 `<|extra|>` 携带存在性:

```
<|assistant|><|tool_calls|>[...]<|extra|>{"__content__":null}
<|user|><|extra|>{"__content__":""}
<|user|><|extra|>{"__content__":{"__missing__":true}}     ← 原文没有 content 键
```

`extra` 同时承载无法映射到上述字段的原始键,做到**不静默丢数据**。

## 4. 分块与块哈希

**完全照搬 vLLM Automatic Prefix Caching**,没有自创算法。

参考:<https://docs.vllm.ai/en/v0.8.3/_sources/design/v1/prefix_caching.md>

### 4.1 vLLM 做什么

文档原文的图示与规则:

```
       Block 1: |<--- block tokens ---->|
       Block 2: |<------- prefix ------>| |<--- block tokens --->|
       Block 3: |<------------------ prefix -------------------->| |<--- block tokens ---->|
```

1. **定长块**,块边界只由位置决定,与内容无关。
2. **块哈希 = hash(父块哈希 + 本块 tokens + 额外哈希)**:

   ```
   block_hash = hash(parent_hash, block_tokens, extra_hashes)
   ```

   父哈希让相同内容挂在不同前缀下得到不同哈希——这就是"前缀"语义。

   本层目前**不用** `extra_hashes`:vLLM 用它区分 LoRA ID 与多模态输入,
   而这层工作在字节上、不感知 LoRA/多模态。形式上保留位置但不引入空参数,
   等真有第二种 renderer 需要隔离块空间时再加。
3. **只缓存满块**("We only cache full blocks")。

DeepSeek 侧对应的是**按固定 token 间隔落盘**(见
[上下文硬盘缓存](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)),
同样是固定间隔。

### 4.2 本层的实现

```python
BLOCK_SIZE    = 512                    # 字节
BLOCK_ID_SIZE = 16                     # 128 bit
_HASH_NAME    = "blake2b"

block_hash(block, parent_hash=b"") = blake2b(parent_hash + block)
```

本层工作在**字节**上,因为网关拿不到 tokenizer。

哈希用 blake2b 而非内置 `hash()`:Borg 官方文档明确要求块 id 必须是**密码学强哈希**,
且内置 `hash()` 带进程随机盐,不能跨进程复用缓存。

### 4.3 `BLOCK_SIZE` 为什么是 512 而不是照抄 16 token

vLLM 的 16 token 换算成中文约 48 字节,直接照抄会得到 48 B 的块。v3 里块太小有两处代价:

1. **尾块要每轮重发**。只有满块能进缓存,不满的那截每次追加都可能变,所以热请求
   总要重发 `上下文长度 mod 512` 字节(平均 256 B)。
2. **走链跳数 = 上下文 / 块大小**。每跳是一次 GET,存储读成本与块数成正比。

同样 800 KB 上下文(§9 实测 829 KB = 1,774 块):

| block_size | 块数(走链跳数) | 每轮重发的尾块上限 | 判断 |
|---|---|---|---|
| 48 B | 17,706 | 47 B | 跳数 10 倍,省下的尾块可忽略 |
| 64 B | 13,280 | 63 B | 同上 |
| 128 B | 6,640 | 127 B | 跳数 4 倍 |
| 256 B | 3,320 | 255 B | 跳数 2 倍 |
| **512 B** | **1,774** | **511 B** | **取这一档** |
| 1024 B | 887 | 1,023 B | 尾块浪费 0.12% |
| 4096 B | 221 | 4,095 B | 尾块浪费 0.5% |

512 是在「尾块浪费可忽略(≤0.06%)」与「走链跳数可控」之间的折中,同时与
DeepSeek 上下文硬盘缓存、vLLM 前缀缓存那套「固定间隔、只缓存满块」的粒度同量级。

> v2 时代还有一条理由:每块要付 `1+16+4 = 21` 字节帧头,48 B 的块光帧头就占 35%。
> **v3 已经没有帧了**(§5.2),这条理由随线缆一起消失;上表的依据全部是走链成本与尾块浪费。

### 4.4 已否决的方案:CDC(内容定义分块)

早期实现过 buzhash 的 CDC(滚动哈希找切点),**已整体移除**。否决理由:

- DeepSeek 与 vLLM 都用固定间隔,不用内容定义切点。
- CDC 必须逐字节计算滚动哈希才能找切点,实测只有 **0.66 MB/s**(2.5MB 请求要 4 秒);
  定长切块是 **486 MB/s**。
- 对话场景天然是**尾部追加**,前缀不动——恰是定长块最有利的形态。
- 那版还错把 `max_size` 设成等于 `avg_size`,35% 的块退化成硬切,
  等于付了 CDC 的全部代价却只拿到部分收益。

## 5. 线缆格式

`Content-Type: application/x-tail-v3`。请求体就是**渲染文本的一段原始字节**——
不是 JSON,不是帧,没有任何逐块元数据。

### 5.1 请求

```
POST /v1/chat/completions
Content-Type: application/x-tail-v3
X-Tail-Session: 3f2ab0c9...            # 会话键 = 渲染文本首块的块哈希(16 B,hex)
X-Tail-Have: 46208;9c1e77d3...         # 可选:客户端认为网关已持有前 46,208 字节,
                                       #       且那段前缀的链尾哈希是 9c1e77d3...
<body>: 渲染文本第 L 字节之后的全部字节(纯文本,原样)
```

- 首次请求不带 `X-Tail-Have`(或值为空)= 从 0 开始,body 就是整段渲染文本。
- `X-Tail-Session` 用内容寻址:首块哈希。同一段 `tools`+`system` 前缀的会话天然同键,
  客户端不必发明 id。
- L 必须是 512 的整数倍(网关按 `L - L % 512` 对齐,不信任客户端声称的未对齐边界)。

### 5.2 响应

```
200 OK
X-Tail-Version: 3
X-Tail-Have: 51456;71b0c4ae...         # 下一轮的凭据,服务端是唯一权威
X-Tail-Status: hit                     # hit / miss / degraded,仅供监控
X-Tail-Hit: 0.998                      # 本轮前缀命中率(按字节)
```

前缀失效(块被淘汰/TTL 过期/存储被清)时:

```
409 Conflict
X-Tail-Version: 3
X-Tail-Status: degraded
X-Tail-Retransmit: 1
```

客户端收到 `X-Tail-Retransmit` 就作废该会话凭据,把全文重发一次(§8)。

### 5.3 为什么没有帧了

v2 的每块 `17 B` 引用帧存在的原因只有一个:**切块与哈希在客户端做**,
网关不知道客户端用的块边界,必须由客户端逐块告诉它「这段我用的是哪个块」。

v3 把切块与哈希整体搬到网关(§6.0 ⑤⑥),于是:

| 需求 | v2 的做法 | v3 的做法 |
|---|---|---|
| 告诉网关「这段我已有」 | 逐块发 17 B 引用帧 | 一个头 `X-Tail-Have: L;H` |
| 告诉网关「这段是新的」 | 逐块发 529 B 新块帧(自带 `block_hash`) | 不需要:网关自己切、自己算 |
| 拼接顺序 | 帧序列即顺序 | 位置即顺序(文本是连续的) |
| 全命中的线上体积(829 KB 上下文) | 1,774 × 17 B ≈ 30 KB | **315 B**(只剩不满一块的尾巴) |
| 固定开销 | 上下文的 3.3%(理论下限) | **≈ 0** |

这是 v3 最重要的简化:**线上不再有「本层自己的格式」**,只有一个头和一段文本。
文本本身就是要转发给上游的 prompt,所以冷启动体积甚至**小于**原生 JSON
(实测 38,262 B vs 40,141 B,少 5%,省掉的是键名与标点)。

### 5.4 兼容性

`X-Tail-Version: 3` 与 v2 **不兼容**。网关按 `Content-Type` 判定是否走本层
(`wants_blocks`):不是 `application/x-tail-v3` 的请求原样透传,所以同一个网关可以
同时服务 v2 客户端(旧的帧流由旧版本处理)、v3 客户端与完全不接入本层的 SDK。

## 6. 传输管线(v3:hash 在网关算,存储用 Redis 链)

> **状态**:本节描述的 v3 **已经落地**,代码与本节一致。v2 的帧流线缆已删除,
> 两版不兼容(`X-Tail-Version` `2` → `3`)。

**整条链路全程流式**。没有任何一步会先把整个请求体收进内存。

### 6.0 全景图:hash 在哪算、缓存何时读写、字节怎么走

```
【客户端】只发字节,不算块哈希

  OpenAI SDK
    │  JSON body(bytes)
    ▼
  ① TailTransport.handle_request
    │    json.loads → payload    ← 整条链路上唯一一次整包物化(§6.6)
    ▼
  ② render.iter_render(payload)
    │    messages JSON → 一维文本片段流;确定性渲染是全部缓存的前提
    ▼
  ③ 取本会话的前缀凭据 (L, H),并**自检前缀没变**
    │    来源:上一轮响应的 X-Tail-Have 头;按会话键索引,每会话 24 B
    │    自检:边渲染边算父链哈希,走到第 L/512 块时与 H 比对
    │      相等 → 前缀逐字节相同,从 L 往后发
    │      不等 → 前缀变了(compact / 改中间消息 / 改了顶层参数)
    │             凭据作废,从 0 重发
    │    ★ 只做**只读校验**:客户端不写任何哈希;0.89 ms / 242 KB,O(1) 内存
    ▼
  ④ 发送:请求头 X-Tail-Have: L;H   X-Tail-Session: <会话键>
          body = 渲染文本第 L 字节之后的原始字节(不是帧)
          ★ 全命中时线上只剩「不满一块的尾巴」:829 KB 上下文计算值 315 B
    ▼
  ⑤ 文本片段按 ~16 KB 合并后写 socket(少 TLS record / 少 syscall)
     HTTP/1.1 chunked;Content-Type: application/x-tail-v3

【公网】一个请求头 + 尾部字节。上行是这里唯一稀缺的东西。

【网关】hash 在这里算

  ⑥ request.stream() → _AsyncToSyncBody
    │    有界队列 maxsize=8 提供背压,不会整包落内存
    ▼
  ⑦ 缓存「读」:按 (L, H) 从 Redis 取回整条前缀          ◀◀◀ 唯一外部存储读
    │    一个 Lua 脚本,一次往返,原子完成两件事:
    │      · 沿 blk:{hash} → parent‖content 的链取回前缀的全部内容
    │      · 顺带给这条前缀上所有块续 TTL
    │    H 解析不到(被淘汰/存储清空)→ 409 + X-Tail-Retransmit,客户端从 0 重发
    ▼
  ⑧ 尾部字节从 L 起**按位置对齐**切 512 B 块,并在网关算哈希
    │    block_hash = blake2b(parent_hash ‖ block)[:16]
    │    父链的起点就是 H —— 所以「前缀语义」由位置和链共同保证
    │    链式写回:blk:{hash} → (parent_hash, content)      ◀◀◀ 唯一回写点
    ▼
  ⑨ render.RenderParser.feed(piece)
    │    <|标记|> 切分 + json.loads 还原 → (PARAM | MESSAGE_START | MESSAGE_END)
    ▼
  ⑩ iter_payload_json → _AsyncJsonStream
    │    首片立刻发(不凑批),之后每 256 KB 一批,每条 message 完成即序列化
    ▼
  上游 LLM —— 它不知道 Tail 存在

【响应方向】

  上游 SSE ──── 原样逐块透传 ────> 客户端 SDK
    网关附加 X-Tail-Version / X-Tail-Status / X-Tail-Hit
             X-Tail-Have: L';H'   ← 下一轮的凭据,服务端永远是权威
    凭据失效 → 409 + X-Tail-Retransmit: 1 → 客户端从 0 重发一次(对 SDK 透明)
```

**状态归属**——「谁记得什么」是这套设计的核心:

| 状态 | 谁持有 | 生命周期 | 800 KB 上下文下的大小 |
| --- | --- | --- | --- |
| 渲染文本 | 客户端流式产出、网关流式还原 | 一次请求 | 0(只有片段) |
| 前缀凭据 (L, H) | 客户端,按会话键索引 | 随会话 | **24 B/会话**(与上下文长度无关) |
| 块哈希与父链 | **网关**(Redis) | TTL,Lua 续期 | 16 B 父指针/块 |
| 块内容 | 网关(Redis) | TTL | 822 KB 原始内容 |
| 命中/缺失 | 网关 | 一次请求 | — |

由此得到 v3 的三个性质:

1. **hash 的权威在网关**。客户端不需要「发引用还是发内容」这个决策了——服务端上一轮
   已经告诉它前缀到哪了,它只负责从 L 往后发。但客户端仍保留一份**只读校验副本**:
   每轮重算一次父链哈希,走到第 L/512 块时与 H 比对(1.21 ms / 845 KB,O(1) 内存)。
   没有这一步就无法确认「我渲染出来的前 L 字节 == 服务端持有的前缀」,错一次就是
   静默拼接错误前缀。
2. **投毒在结构上不可能**。存储里的块哈希只由网关算、网关写;客户端的哈希只用于本地
   比对,永不入网、永不入库。
3. **线上开销 ≈ 0**。v2 那个"每 512 B 付 17 B 引用帧 = 上下文 3.3% 的理论下限"
   消失了:引用被压缩成一个请求头。

代价与风险(必须一起看):

- **服务端每请求都要走一遍链**(829 KB 前缀 = 1,774 跳),且是顺序的、在单线程
  Redis 里。3,333 req/s(10 万在线 / 30 秒一轮)时单实例扛不住,见 §7。
- **凭据有并发问题**:同一会话两个请求同时在飞(工具调用常见)会带回两份不同的
  (L', H')。已用「每会话保留最近 4 条凭据(MRU)」缓解:乱序返回的两份都能匹配上,
  过期凭据只会 miss 不会错拼(§11)。
- **两版线缆不兼容**,需要版本协商与灰度(按 `Content-Type` 分流,见 §5.4)。

### 6.1 客户端接入点:TailTransport

第 ② 步的入口是 `TailClient.prepare(payload)`，但上层（`openai` SDK）
只会交出**已经序列化好的 JSON body**。要把它换成「凭据 + 尾部字节流」，需要一个
「body 改写」的接入点。

选 `httpx2` 的 **transport**，不选 openai SDK 的内部方法：

| 接入点 | 可行性 |
| --- | --- |
| monkey-patch `openai` 私有方法 | 旧实现的做法。旧协议只需改 `options.json_data` 加个头，可行；新协议要把整个 body 换成**流式字节流**、还得把响应头里的凭据喂回本地表，SDK 内部改不动 |
| 应用层手写 HTTP | 可行但要求用户重写全部调用代码，违背「现有代码不变」 |
| **`httpx2.Client(transport=...)`** | ✅ 公开扩展点，SDK 内部结构一行不碰，只替换「字节怎么发出去」 |

`TailTransport.handle_request` 做的事：

```
request.read()                  → 已序列化的 JSON body
json.loads                      → payload dict
client.prepare(payload)         → 凭据 (session, L, H) + 尾部字节流(不落地、不拼大 bytes)
Content-Type → application/x-tail-v3,带上 X-Tail-Session / X-Tail-Have,删掉 Content-Length(改 chunked)
内层 transport.handle_request   → 真正发出
200 响应                        → update_from_headers():把服务端给的下一轮凭据存回本地表
响应带 X-Tail-Retransmit        → client.invalidate() 后全量重发一次
```

只拦 `/chat/completions` 且 `Content-Type` 含 `json` 的请求；其余（`/models`、
embeddings、文件上传）原样透传。body 不是合法 JSON 时也不猜，原样发出。

#### 本地状态:每会话 24 B,不存块、不算块哈希

| 项 | 量 |
| --- | --- |
| 每个会话 | `(L, H)` = 前缀字节数 + 链尾摘要 = 8 + 16 = **24 B**,MRU 保留 4 条 |
| 1,000 个活跃会话 | **96 KB** |
| 与上下文长度的关系 | **无关** |

作为对照,v2 是「每块一条 16 B 哈希」:131 B/块、800 KB 会话 210 KB、
1,000 个会话 205 MB,而且无淘汰。

三条边界:

1. **凭据只由服务端给**。客户端从不自己算 `(L, H)`——它只在响应头里读
   `X-Tail-Have`,绑定到本会话。服务端永远是权威。
2. **发送前必须先自证前缀没变**。客户端持有 `(L, H)`,但没有中间块的摘要,
   所以它重渲染并逐块算父链哈希,走到第 `L/512` 块时与 `H` 比对:
   相等 → 前 L 字节逐字节相同(渲染确定性),从 L 往后发;不等 → 凭据作废,从 0 发。
   **这是游戏规则的关键**:客户端永远只做只读校验,绝不声称任何新哈希。
3. **会话键** = 渲染文本首块的块哈希。它同时是内容寻址的会话标识(同前缀同键)
   和响应绑回请求的索引;客户端在 `X-Tail-Session` 里带上,网关按它回显凭据。

**必须复用同一个 client 实例**——凭据表挂在 `TailClient` 上,每轮新建
`OpenAI(...)` 就等于永远冷启动(实测:6 轮合计 14,109 B vs 5,405 B,差 62%)。
`TailTransport` 因此随 `http_client` 活,与 SDK client 同寿命。

### 6.2 启动 HTTP chunked 到上游

网关用 `httpx2` 的 `AsyncByteStream` 适配:每次 `next()` 得到一个 JSON 片段就
立刻 `yield`,不等全部生成完。解码是 CPU 密集的同步代码,放进**单线程**
`ThreadPoolExecutor`(惰性迭代器非线程安全,用默认线程池会丢消息)。

### 6.3 普通 JSON 透传路径

`Content-Type` 不是 `application/x-tail-v3` 时,网关**原样转发**,同样直接透传
`request.stream()`——不先收齐。用于灰度对比与排障。

### 6.4 流式性的实测证据

body 34610B / 34 片,每片间隔 20ms:

```
客户端全部发完耗时:         674ms
上游收到首片时,客户端已发出:  2/34 片      ← 才发出 6% 就开始转发
上游 首片 → 收完:            673ms
```

若先 `await request.body()` 收齐再转发,上游首片会在 **674ms** 之后才到。
这条已固化为测试 `test_upstream_receives_before_client_finishes`,
并验证过:把实现改回收齐再转发,该测试立即失败。

---

### 6.5 分片大小:16 KB 的依据

v3 的请求体是连续文本,本身就可以任意切片;切片的粒度只影响「每 chunk 的固定开销」。
v2 时这里更尖锐(每个 17 B 引用帧都会变成一个 chunk),v3 已经没有那种碎法,
但**网关侧读存储、重建 JSON 也是按片推进的**,片太小仍会让每片都过一次线程池往返。

取 16 KB 有两个依据:

1. **和 nginx 的默认缓冲一致**。`client_body_buffer_size` 默认 `8k|16k`,
   [文档](https://nginx.org/en/docs/http/ngx_http_core_module.html)原文是
   「等于两个内存页,x86 与 x86-64 是 8K,其它 64 位平台通常是 16K」。
   取这一档,主流反向代理不需要为 Tail 调参。
2. **本地实测 ≥8 KB 后无差别**。888 KB 热请求按 4K/8K/16K/32K/64K 合并:

   | 合并大小 | 片段数 | 端到端中位数 |
   |---|---|---|
   | 4 KB | 7 | 38.4 ms |
   | 8 KB | 4 | 39.1 ms |
   | 16 KB | 2 | 37.3 ms |
   | 32 KB | 1 | 37.7 ms |
   | 64 KB | 1 | 37.7 ms |

   取 16 KB 而不是更大,是为了让首个片段尽早发出——对端收到第一个块就能开始
   解码,没必要为了少几个 chunk 去推迟首字节。

真正决定网络分段的是 TCP MSS(~1460 B)与 TSO/GSO,不是这里的合并大小;
这一层只影响每 chunk 的固定开销。

### 6.6 客户端唯一一次整包物化:`json.loads`

链路其余部分全是流式的,只有 ① 这一处必须把 body 解析成 dict——因为 `openai` SDK
交出来的是**已经序列化好的 JSON bytes**,而渲染器需要结构。这是接入点位置决定的,
不是实现疏忽。实测(845 KB 请求体,7 次取最小值):

| 项 | 量 |
| --- | --- |
| `json.loads` | **0.56 ms**(占整条客户端路径 2.88 ms 的 19%) |
| 解析后常驻 | **0.55 MB** dict(受编码影响:中文 UTF-8 3 B/字 → 内存 UCS-2 2 B/字) |
| 解析峰值 | **2.47 MB**(请求体的 3.0 倍) |
| dict 存活期 | 整个请求期间(前缀客户端生成器持有 payload 引用) |

要消掉它有三条路,代价都大于收益,所以暂时接受并记录在案:

| 方案 | 收益 | 代价 |
| --- | --- | --- |
| 换 `orjson` | `loads` 快 5~10 倍 | 新依赖;内存不变,也省不掉 dict |
| 流式 JSON 词法器(`ijson` 或自写) | 消掉 dict(2.47 MB → 单条 message) | 新依赖或自写解析器;渲染器要改成事件式 |
| 挂到 SDK 序列化之前 | 彻底不解析 | 要 monkey-patch SDK 私有方法,已否决(§6.1) |

只在服务端嵌 SDK 的场景(3,333 req/s)下才值得做:那时 0.56 ms × 3,333 ≈
**1.9 核**纯浪费,常驻 `0.55 MB × 并发`。

### 6.7 v2 → v3 的实现对照

| 阶段 | v2(已删除) | v3(当前代码) |
| --- | --- | --- |
| ① 接入点 | `TailTransport`(httpx2 transport) | 同 |
| ② 渲染 | `render.iter_render` | 同 |
| ③ 本地状态 | `set[bytes]` 已知块集合,131 B/块,无淘汰 | 每会话凭据表 `(L, H)`,24 B/条,MRU 保留 4 条 |
| ④ 线上格式 | 帧流:17 B 引用帧 / 529 B 新块帧 | 请求头 `X-Tail-Have` + 一段原始文本字节 |
| ⑤ 合并 | 引用帧合并 16 KB | 文本片段合并 16 KB |
| ⑥⑦ 存储读 | `get_many(refs)` → Redis MGET;扁平 `blk:{hash} → 内容` | 按 `(L, H)` 走链(Lua)→ MGET;链式 `blk:{hash} → parent‖content` |
| ⑧ 切块/哈希 | 客户端 `BlockHasher` | **网关**按 L 对齐切块 + 父链哈希(客户端只做只读自检) |

| 指标 | v2 | v3 |
| --- | --- | --- |
| 829 KB 上下文全命中线上体积 | 30,158 B | **315 B** |
| 线上固定开销 | 上下文 3.3%(理论下限) | **≈ 0** |
| 客户端每会话状态 | 210 KB,无淘汰 | **24 B** |
| 客户端是否发哈希 | 发(服务端只能信任) | **不发,结构上不可能投毒** |
| 网关每请求额外 CPU | 只解码 | 切块+哈希+走链,829 KB ≈ 24 ms(§9) |
| 失败恢复代价 | 重发全文 | 重发全文(同样) |

## 7. 存储:Redis 链式块(v3)

### 7.1 链和内容在同一个 value 里

这是与 v2「扁平集合」的本质区别:

```
p:{block_hash_hex} → parent_hex(16 B, ASCII=32)
b:{block_hash_hex} → content(≤ 块大小)
```

**链和正文分开放**(v4):走链只需要父哈希,所以每跳只搬 16 字节;正文由一条 MGET
批量取回。早先把两者拼在同一个 value 里,走一条 829 KB 前缀就等于在 Lua 里白搬 887 KB。

因为 `block_hash = blake2b(parent_hash ‖ content)`,所以给定链尾摘要 `H`,
就等价于拿到了**整条前缀的入口**:

```
H → block[1773] → parent → block[1772] → ... → block[0] → 0…0(链根)
```

父哈希在 `p:` 的 value 里是**定长 hex**(链根写成 16 个 `\x00`),走链脚本可以直接把
读到的 value 当下一跳,不需要额外编解码。

于是 v2 §10 里那句「顺序信息与帧序列重复、所以不需要链」自动失效:
v3 没有帧序列了,顺序信息**无处可去**,链是它的唯一载体。

### 7.2 两个实现,一个生产后端

| 实现 | 说明 |
|---|---|
| `RedisChainStore` | **生产唯一后端**:`p:`/`b:` 两个命名空间 + 两个 Lua 脚本 |
| `MemoryChainStore` | 进程内字典,**仅测试替身**(不落盘、不跨进程) |

`make_store("redis://host:6379/0", ttl=…)` → `RedisChainStore`;`make_store("")` 只在测试里用。

### 7.3 写:一个脚本写完整串块

```lua
-- KEYS = [b:key_1..b:key_n, p:key_1..p:key_n];ARGV[1] = TTL 秒
-- ARGV[2..n+1] = 正文;ARGV[n+2..2n+1] = 父哈希 hex
local n = #KEYS / 2
local ttl = tonumber(ARGV[1])
for i = 1, n do
  if ttl > 0 then
    redis.call('SET', KEYS[i], ARGV[i + 1], 'EX', ttl)          -- 正文
    redis.call('SET', KEYS[n + i], ARGV[n + 1 + i], 'EX', ttl)  -- 父链
  else
    redis.call('SET', KEYS[i], ARGV[i + 1])
    redis.call('SET', KEYS[n + i], ARGV[n + 1 + i])
  end
end
return n
```

**不能用 pipeline**:非事务管线只保证「按顺序发出去」,中途出错或进程被杀会留下半条链,
而网关随后会把这段前缀的 tip 告诉客户端——对端下一次拿着悬挂的 tip 来,`resolve`
返回 None,表现为「刚发过的内容立刻 miss」。脚本是原子的:要么整串可见,要么全不可见。

块多时由调用方分批(`codec.BLOCK_BATCH = 256`),避免单个脚本长时间占住实例。

### 7.4 读:一个脚本走链 + 续期

```lua
-- KEYS[1] = "p:" 前缀,KEYS[2] = "b:" 前缀
-- ARGV[1] = tip hex;ARGV[2] = 块数;ARGV[3] = TTL 秒
local pk, bk, cur = KEYS[1], KEYS[2], ARGV[1]
local n, ttl = tonumber(ARGV[2]), tonumber(ARGV[3])
local ids = {}
for i = 1, n do
  local v = redis.call('GETEX', pk .. cur, 'EX', ttl)  -- 读父哈希 + 续链 TTL(一条命令)
  if not v then return {} end                          -- 前缀不完整 → miss,让客户端重发
  redis.call('EXPIRE', bk .. cur, ttl)                 -- 正文 TTL 在同一脚本里一起续
  ids[#ids + 1] = cur
  cur = v                                              -- 下一跳
end
return ids
```

一次调用同时解决三件事:走链、续链 TTL、续正文 TTL。热心跳也在脚本里做——
每跳依赖上一跳的结果,由网关逐跳发命令就是 N 次网络往返。

两把 key 的 TTL 必须一起续,否则会出现「链还在、正文先死」:那样 `resolve` 成功但
`get_many` 缺块,上层仍然要判 miss 让客户端重发——正确但更慢。

脚本**不做拼接**:返回块哈希列表,内容由网关侧用 MGET 批量取、流式拼接。
在 Lua 里拼 800 KB 字符串会阻塞整个 Redis 实例。

「整条前缀一次 Lua 读完」也实测过(1,774 块),结论是不值得:

| 读法 | 一次读 |
| --- | --- |
| 现状:**走链脚本(1 往返,原子)+ MGET(1 往返)** | 7.99 ms |
| 合并成单脚本、正文按块散表返回 | 7.78 ms(−3%) |
| 合并成单脚本、正文在 Lua 里 `table.concat` 返回 | 12.72 ms(+59%) |

大头是 1,774 次 `GET + EXPIRE`,不是往返次数;855 KB 无论如何要搬一次。散表版省的
0.2 ms 在噪声内,拼接版还要在 Lua 里拷 855 KB、把实例阻塞 12.7 ms(尾延迟更差)。
所以固定为:走链一个脚本 + 正文一条 MGET。

### 7.5 实测成本:走链是 O(块数)

`tools/bench.py` 的「Redis」一段,夹具是 829 KB 前缀。走链是 O(块数),所以
**块大小决定单实例上限**:

| 块大小 | 块数 | 写整串(2 key/块) | 走链 | MGET | **读一次** | 单实例上限 |
|---|---|---|---|---|---|---|
| 512 B | 1,774 | 9.4 ms | 3.8~4.4 ms | 2.6~3.2 ms | **7.3~9 ms** | **110~140 req/s** |
| 2 KB | 443 | 6.9 ms | 1.5~2.0 ms | 1.9~2.2 ms | **3.9~5.3 ms** | **190~260 req/s** |
| 4 KB | 221 | 5.1 ms | 1.1~1.4 ms | 1.1~1.4 ms | **2.6~2.9 ms** | **350~390 req/s** |
| 8 KB | 110 | — | 0.9~1.0 ms | 0.9~1.1 ms | **1.7~1.9 ms** | **520~590 req/s** |

块放大的代价只有一个:热请求每轮重发不满一块的尾巴(512 B 时平均 256 B,4 KB 时
平均 2 KB,占 829 KB 的 0.25%)。所以块大小由「上下文长度 × 尾块占比」定,不是常量。

单个 key 的操作成本(1,774 次,脚本内):`GET` 1.7 ms、`GETEX` 2.2 ms、
`GET+EXPIRE` 3.0 ms、`GETEX+EXPIRE` 3.6 ms —— 续期本身就是每块一次额外调用,
这是「分开存 + 两把 key 都续期」在 512 B 块下不划算的原因,也是块该放大的依据。

规划公式(按会话键分片,线性):

```
所需 Redis 实例数 ≈ 目标 req/s ÷ 单实例上限
```

| 场景(3,333 req/s) | 需要实例(512 B 块) | 需要实例(4 KB 块) |
| --- | --- | --- |
| 829 KB 上下文 | 27 个 | **10 个** |
| 242 KB 上下文 | 8 个 | 4 个 |
| 66 KB 上下文 | 3 个 | 2 个 |

### 7.6 只存满块

vLLM: "only cache full blocks"。不满的尾块内容会被后续追加改变,存它没有意义,
所以热请求每轮重发 `上下文长度 mod 512` 字节(平均 256 B,§4.3)。

因为只存满块,`X-Tail-Have` 里的 L 永远是 512 的整数倍;网关收到未对齐的 L 会向下对齐。

## 8. 降级与恢复

任何一块取不到(存储被清、服务重启、TTL 过期、LRU 淘汰),**立刻失败**,
不走「跳过继续解」。触发点在 v2 是解码器查不到引用块,v3 是按 `(L, H)` 走链
取不到完整前缀——两者行为一致:



1. 抛异常时请求体上传被中断,httpx 直接断掉上游连接——**上游拿不到完整请求,
   不会开始推理**。
2. 网关回 HTTP 409 + `X-Tail-Retransmit: 1` + `X-Tail-Status: degraded`
   + `X-Tail-Hit`(命中率快照)。
3. 客户端 `invalidate()` 丢掉该会话凭据,把全文当新一轮发。请求体本身就是完整正文,
   所以**不需要任何补发协议**。

为什么不「跳过缺块、拼出能拼的部分照常转发」——两种洞都不能接受:

| 洞的位置 | 跳过后的后果 |
| --- | --- |
| 落在 UTF-8 多字节字符中间(512 B 块边界必然切开汉字) | 后续片段首字节非法 → `UnicodeDecodeError` → 客户端看到传输层异常,**不是**重发信号 |
| 落在 message 边界 | 拼出的 prompt 语义已变,但仍是合法 JSON → **静默转发给上游**,白跑一次完整推理再把结果丢掉 |

另外,缺块是在生成器**结束时**才暴露的;早期实现在异常路径上根本走不到「设置重发头」
那一步,所以 409 那条路永远不生效。现在 `DecodeSession` 在抛异常之前先落统计快照,
`serve._handle` 再把它翻译成 409。

还有一个**必须成对**的细节:网关抛异常时要先取消请求体泵、排空队列
(`_AsyncToSyncBody.stop()`),否则上游可能已经收到半个 body 开始 prefill。
`test_mid_block_miss_returns_409_without_inference` 断言的就是「缺块时上游一次推理都没跑」。

### 测量口径(重要)

统计用**两种时间**,混用会得出互相矛盾的结论:

| 口径 | 用什么 | 为什么 |
|---|---|---|
| 吞吐表 | `time.process_time()`(**CPU 时间**),计时区间关 GC,取 7 次最小值 | 机器空闲时它和 wall 一致(本次 18.8 vs 18.8 ms);机器有负载时 wall 会被调度与分配器抖动放大 3~10 倍(load ≈ 55 那次:CPU 20.4 ms 对 wall 27~471 ms) |
| 端到端表 | `time.perf_counter()`(**wall clock**) | 用户感受到的等待就是 wall;负载同样会抬高绝对值,表内比值仍可比 |

Redis 那两段用 wall(成本在网络往返),取 15 次最小值。所有数字取自同一次运行
(`load average ≈ 22 / 10 核`),负载更高时绝对值只会更大。**同一脚本两次运行之间,
CPU 行抖动约 ±20%**(888 KB 解码实测 19~25 ms),所以对机器敏感的几行给的是区间;
结论只依赖数量级,不受影响。

### 真实对话周期(200 KB → 800 KB → compact → 200 KB)

夹具含真实规模的 `tools`(38 KB)与 `system`(8 KB)固定前缀:

| 轮次 | 原始 JSON | 上行 | 占比 | 前缀命中率(按字节) |
|---|---|---|---|---|
| 起点 ~200 KB(冷) | 286,073 | 285,888 | 99.9% | 0.0% |
| 增长中 ~455 KB | 466,262 | 180,267 | 38.7% | 61.3% |
| 增长中 ~690 KB | 706,514 | 240,143 | 34.0% | 66.0% |
| 涨到 ~807 KB | 826,640 | 120,065 | 14.5% | 85.5% |
| **compact 之后** | 280,008 | 279,918 | 100.0% | 0.0% |
| compact 后 +1 轮 | 340,071 | 60,391 | 17.8% | 82.2% |
| compact 后 +2 轮 | 400,134 | 60,512 | 15.1% | 84.9% |

**compact 那一轮会全量重发,而且是必然的**:客户端手里只有 `(L, tip)`,没有中间块的
摘要,证不出「L 之前那段前缀仍然一致」,只能从头发。这是「客户端状态 O(1)」的代价:
重置类事件(compact、改中间消息、改 top-level 参数)各付一次全文,其余每轮都是增量。

注意「增长中」那几轮的命中率不是 100%:基准里只把每第 4 次增长送去请求,
中间没经过网关的内容自然不会被缓存——这是夹具形态,不是协议缺陷。

### 速度(242 KB 请求,CPU 时间,7 次最小值)

| 环节 | 吞吐 | 单次耗时 | 备注 |
|---|---|---|---|
| 渲染 JSON → 文本 | 552 MB/s | 0.45 ms | 客户端 |
| 切块 + 链式哈希 | 635 MB/s | 0.39 ms | 两侧都要做;0.8 µs/块 |
| 客户端 prepare(冷) | 556 MB/s | 0.45 ms | 渲染 + 首块哈希 + 重渲染 |
| 客户端 prepare(热) | 317 MB/s | **0.78 ms** | 渲染 + **全量父链自检** |
| 网关解码(冷) | 49 MB/s | 5.12 ms | 哈希 + 写链 + 反渲染 + 重建 JSON |
| 网关解码(热) | 49 MB/s | 5.08 ms | 走链 485 跳 + 取块 + 反渲染 + 重建 JSON |

**热路径比冷路径贵**,这点反直觉但正确:冷启动时客户端只哈希首块(那是会话键),
然后直接重渲染全文;热路径要把整条前缀的父链哈希重算一遍才能确认 `(L, tip)` 仍然成立。
0.78 ms / 242 KB 买到的是「服务端无需信任客户端的任何哈希」。

客户端唯一一次整包物化:`json.loads` 同一份 242 KB 是 **0.17 ms**,常驻 0.25 MB、
峰值 0.75 MB(3 倍),见 §6.6。

|---|---|---|---|
| 66 KB | 1.2 ms | 3.3 ms | 2.7× |

**回环上 Tail 更慢**:透传只是搬字节,Tail 要解码 + 反渲染 + 重建 JSON(888 KB 约 20 ms CPU),

### 慢上行链路:TTFT 的前置段

| 2 Mbps | 3,650 ms | **23 ms** | **155.4×** |

上行从 888 KB 降到「1 KB 量级」,请求提交时间从「按带宽算的秒级」降到「网关解码的几十毫秒」。

### 实现过程中修掉的三个真 bug

都不是「算法慢」,而是**不做真机集成就发现不了**的问题:

| # | 问题 | 现象 | 修法 |
|---|---|---|---|
| 1 | Redis value 里链根的父哈希写成空串 | value 变成 `"" ‖ content`,读回来 `v[32:]` 吃掉根块正文前 32 字节——**每条前缀的第一块都是坏的** | 父哈希定长 32 B hex,链根写 16 个 `\x00` |
| 2 | `BlockHasher` 缓冲的半块被消费却没发出 | 续传时文本被截断,块边界切开汉字就 `UnicodeDecodeError` | `take_pending()` 把缓冲交回,与后续渲染片段一起发 |
| 3 | `MemoryChainStore` 用 `list.remove` 做 LRU | 单次读取退化成 O(n²):1,774 块读一次 **137 ms**,把「网关解码」整行污染成超线性 | 换 `OrderedDict.move_to_end` |

第 3 条是基准脚本自己踩出来的:它先表现为「888 KB 比 418 KB 慢 4 倍」,查下去才发现
是测试替身的问题,不是协议的问题。

### 测量方法上的两个坑(都踩过)

1. **不要用批量 `timeit` 的均值**:GC 暂停会污染批次均值。同一调用批量测 1.1 ms,
   单次测 0.78 ms。现在每次计时前 `gc.collect()`、区间内关 GC、取最小值。
2. **机器状态会彻底污染 wall clock**:swap 用满且 load 53 时,同一个 800 KB 请求能测出
   wall 150~300 ms 而 CPU 只有 17 ms。本次实测同样存在:CPU 20.4 ms 对 wall 27~471 ms。
   所以吞吐表用 CPU 时间,端到端表用 wall 并记录负载。

## 11. 审核清单

### 已解决(每条都能在代码/测试里指到)

| 问题 | 结论 |
|---|---|
| **哈希投毒**(v2 阻断项):服务端无法校验客户端声称的块哈希 | **结构上消除**。v3 客户端一个哈希都不发:`X-Tail-Session` 与 `X-Tail-Have.tip` 只用于**查**,新块哈希全部由网关算、网关写。客户端即使发错,也只是落到一棵无关的链上(等于 miss),不会污染别人的块 |
| 凭据追加判定(compact / 改中间消息) | 客户端发之前**重算整条前缀的父链哈希**,只有恰好走到某个已知 `(L, tip)` 才复用;对不上就从 0 发。`TestPrefixClient::test_edit_middle_falls_back`、`test_changed_param_refalls` 覆盖 |
| 并发乱序(同一会话两个请求在飞) | 每会话保留**最近 4 个凭据**(MRU),乱序返回的两个 `(L', tip')` 都能被后续请求匹配上;过期凭据只会 miss,不会错拼。`test_bounded_credentials` 覆盖 |
| 会话键冲突(首 512 B 相同) | **按特性处理**:会话键就是首块哈希,内容寻址。共用凭据不产生错误——服务端按 `(L, tip)` 走链,内容不同必然链尾不同,匹配不上就退化成 miss |
| 走链吞吐(1,774 跳/请求) | 已测:Redis 单实例约 **90~140 req/s**(829 KB 全量前缀、512 B 块),4 KB 块 **290~366 req/s**;3,333 req/s 需要按会话键分片(§7.5) |
| 409 恢复 | 客户端收到 `X-Tail-Retransmit` 丢掉凭据、全文重发一次,对调用方透明。代价是一次完整上行(不额外增加推理——`test_mid_block_miss_returns_409_without_inference` 断言上游一次推理都没跑) |

### 看着像代价,其实是正常行为

| 行为 | 说明 |
|---|---|
| compact / 改中间消息 / 改顶层参数那一轮全文重发 | **前缀本身变了**,客户端只持有 `(L, tip)`、没有中间块摘要,证不出旧前缀仍一致,只能重传——不是缺陷。Agent 本来就会频繁 compact / 改消息 / 改参数,这是**常规路径**:一次完整上行(§9 实测 280 KB),下一轮立即恢复增量。这是「客户端状态 O(1)」的对称面;要消掉它得存中间摘要(回到 v2 的 210 KB/会话)或让网关下发检查点(每请求多几百字节) |

### 记录项(关系不大,先记着)

| 项 | 量 | 说明 |
|---|---|---|
| 客户端 `json.loads` 一次整包 | **0.17 ms** / 242 KB,峰值 3 倍内存 | 要渲染成文本就必须解析 JSON,接入点固有,见 §6.6;占端到端 <1% |

### 仍然存在、而且是有意接受的代价

| 代价 | 量 | 为什么不修 |
|---|---|---|
| 网关 CPU 随上下文线性增长 | 888 KB ≈ 21 ms | 走链 + 反渲染 + 重建 JSON;只能靠分片、放大块、截断 |
| 前缀存储按块计费 | 每块 ≈ `32 + content` B + Redis 开销 | 只存满块、TTL 续期;长会话的存储与其上下文同阶 |

### 上线前必须定的运维参数

1. **TTL 取值**:块 TTL 决定「会话空闲多久之后第一轮退化成全量」。经验上取 30~60 分钟。
2. **块大小**:512 B 还是 1~4 KB,决定每请求跳数与尾块重发上限(§7.5)。
3. **Redis 分片键**:按会话键(首块哈希)分片最自然——同一会话的所有块落在同一实例,走链不跨机。
4. **前缀截断**:要不要只保留最近 N 块。截断会降低命中率,但把每请求的走链跳数封顶。

### 建议按这个顺序核对

1. **渲染确定性**:同一 payload 连续渲染 1000 次是否字节完全相同?
   (`TestRender::test_deterministic` / `test_deterministic_ignores_key_order`)
2. **往返保真**:随机 payload 渲染→反渲染是否完全相等?
   (`test_roundtrip_with_hostile_content` 覆盖正文含 `<|user|>`、引号、反斜杠、换行)
3. **流式切块一致性**:任意字节边界喂入,结果是否与一次性切分完全一致?
   (`test_matches_one_shot` / `test_hashes_match_blocked_hashes`)
4. **哈希链**:相同内容在不同前缀下 `block_hash` 是否不同?(`test_block_hash_depends_on_parent`)
5. **前缀复用**:尾部追加时,前面满块的 id 是否全部不变?(`test_append_only_grows_tail`)
6. **全程流式**:上游开始收包时客户端是否远未发完?(`test_upstream_receives_before_client_finishes`)
7. **降级恢复**:存储清空后是否正常降级并要求重发,恢复后是否继续命中?(§8)
