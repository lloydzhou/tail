# Issue: 把 Tail 重构为「文本去重传输层」

> 状态：设计阶段 / 待评审
> 分支：`feat/text-dedup-transport`
> 关联：`docs/DESIGN-chunked-cache.md`（v2.1 链式设计，本文说明为何不沿用）

## 背景

现有 Tail 的做法是：在 OpenAI Chat Completions 请求上扩展 `X-Cache-Hash` / `X-Cache-Prefix-Length` 两个头，body 仍是标准 JSON，只把「前缀之后的消息」当增量发。

这个方案能省流量，但有三个结构性问题（详见下文）。本文提出替代方案：**在 SDK 与上游之间插入一层与 LLM 语义无关的文本去重传输层**——先把 JSON 渲染成固定格式文本，再对文本做内容定义分块（CDC）去重，网关侧流式还原成 JSON。

## 目标

**在走公网的那一段，让数据更小、重复内容尽量不传，以减少带宽、提高上行速度。**

优先级明确：

1. 上行体积（这是唯一硬指标）
2. 实现简单性（不做不必要的语义处理）
3. 可替换性（转换器可换，传输与缓存逻辑不变）

## 为什么不在原来的 JSON 上直接传

### 理由一：JSON 结构冗余无法被前缀缓存消掉

前缀缓存只消掉「重复的部分」。但每个**新增**消息依然带着完整 JSON 结构：

```json
{"role":"user","content":"..."}
```

这些键名、引号、花括号、逗号、转义，对模型是零信息，对带宽是纯开销。在长对话里，结构字符占 body 的比例稳定在 15%~25%。

**换成一维文本后，结构字符消失，只剩少量模板控制符。** 实测（见 §体积估算）：同一份对话文本形态比 JSON 形态小约 20%。

### 理由二：JSON 是树，不适合做内容定义分块

CDC（content-defined chunking）依赖「在任意字节位置判断切点」。JSON 是树形结构，切点落进语法节点会引入大量语义无意义但字节有意义的碎块，导致：

- 块边界不稳定（同样的内容在不同缩进/字段顺序下切点不同）
- 命中率虚高但实际内容无法复用

**渲染成文本后，输入是连续一维字节流，滚动哈希可以在任意字节位置切。** 这是 rsync / git packfile 一直以来采用的形态。

### 理由三：现有「尾部增量」只能处理追加，处理不了任何改写

这是 v2.1 最核心的缺陷：

| 场景 | 尾部增量 | 分块去重 |
|---|---|---|
| 追加一轮对话 | ✅ | ✅ |
| compact / 摘要压缩历史 | ❌ 整条前缀失效 | ✅ 只有被改写区域重传 |
| 编辑旧消息 | ❌ 整条前缀失效 | ✅ |
| 重排消息顺序 | ❌ 整条前缀失效 | ✅ |
| 中间插入 | ❌ 整条前缀失效 | ✅ |

agent 场景里后四类操作非常常见（工具调用循环、上下文压缩、多轮规划）。**尾部增量在这些场景下的回退成本是「全量重传」，而分块去重是「只重传变化的那几块」。**

### 理由四：语义依赖是复杂度的主要来源

现有实现需要理解 role / tools / system 的位置与格式：

- `system` / `tools` 的顶层字段在 OpenAI 协议里根本不存在（system 是 `messages[0]`），导致这两段缓存实际从未生效
- 不同模型族的模板、special token、tools 渲染方式各不相同
- 任何格式变化都需要修改协议层

**中间层如果只认字节，所有这些都不需要处理。** 转换器（JSON → 文本）可以独立替换，传输与缓存逻辑完全不变。

## 方案

### 分层

```
LLM SDK
  └─ 渲染器（Renderer）：messages JSON → 固定格式文本流
       └─ 编码器（Encoder）：文本流 → CDC 分块 → 引用帧 + 新块帧
            └─ 【公网】按原始顺序的帧流
                 └─ 解码器（Decoder）：帧流 → MGET 取块 → 拼成完整文本流
                      └─ 反渲染器（Unrenderer）：文本流 → OpenAI JSON 流
                           └─ 上游推理 API
```

四层职责单一，可独立替换：

| 层 | 输入 | 输出 | 是否懂 LLM 语义 |
|---|---|---|---|
| Renderer | messages JSON | 一维文本 | ✅ 是（唯一懂的地方） |
| Encoder | 文本 | 帧流 | ❌ 只认字节 |
| Decoder | 帧流 | 文本 | ❌ 只认字节 |
| Unrenderer | 文本 | OpenAI JSON | ✅ 是 |

**关键约束：Encoder / Decoder 完全不依赖聊天协议。** 换成 Anthropic Messages、Responses API、甚至任意二进制协议，只需换 Renderer / Unrenderer。

### 三条不变式

**1. 渲染必须确定性。**
同一个 messages 必须渲染成完全相同的文本，否则 `block_id = H(块内容)` 变化，缓存整体失效。
要求：字段顺序固定、可迭代对象顺序固定、模板版本化。

**2. 中间层无语义。**
Encoder / Decoder 不知道哪个字节是 role、哪个是 tools。**这是本方案与原方案的本质区别。**

**3. 缓存缺失只退化，不报错。**
取不到某个 `block_id` 时，把请求当纯文本直传——仍然比原始 JSON 小，只是少了去重收益。系统在缓存全空、存储挂掉、服务重启时都能正常工作。

### 分块参数

```
平均块大小   4 KB     1M token ≈ 4MB 文本 → 约 1000 块
最小块       512 B
最大块       64 KB
block_id     16 字节  内容 SHA-256 截断
分块算法     gear hash（滚动哈希，内容定义）
```

引用列表开销：1000 块 × 17 字节 ≈ 17KB，相对 4MB 约 0.4%。

### 线上格式

路径不变（`POST /v1/chat/completions`），body 为二进制帧流：

```
Content-Type: application/x-tail-blocks
X-Tail-Version: 1

0x01 <16 字节 block_id>        引用：这段内容网关已有
0x02 <4 字节长度> <原始字节>     新块：直传
0x03                           结束
```

**为什么用二进制帧而不是 JSON 包一层：**

- 无二次转义。JSON 里新块内容要转义引号和反斜杠，体积与 CPU 双双翻倍
- 可流式解析。读 1 字节识别类型、读 4 字节得到长度，不需要等整个 body
- 引用帧固定 17 字节，极其紧凑

若先求跑通，可退回 JSON 数组 `["id1","id2",{"c":"..."},"id4"]`，代价是 CPU +30%。**接口层保持一致，后续可平滑替换。**

### 存储

扁平块集合，**没有链、没有 prev 指针、没有引用图**。

```
blk:{block_id} → 块内容       TTL: 无，靠 allkeys-lru 淘汰
```

顺序由请求里的帧序列直接表达，服务端不需要存任何指针结构。因此：

- 不需要访问驱动续期
- 不需要引用计数
- 不需要「链在块在」不变量
- 不需要缺块补发协议
- 不存在部分命中概念（缺块即退化直传）

**默认实现：`dbm`（零依赖）**，与现有 Python 网关一致；可选 `redis` / `kvrocks`（支持 `MGET` 批量取块，一次往返取回全部引用块）。

### 体积估算

基准：1M token ≈ 4MB 文本。

| 状态 | 公网上行体积 | 说明 |
|---|---|---|
| 原始 OpenAI JSON | 4.0 MB | 带键名 / 引号 / 转义 |
| 纯文本直传（缓存全空） | 3.2 MB | 去掉 JSON 结构 |
| 块去重（命中 90%） | 0.4 MB + 17KB | |
| 块去重（命中 99%） | 0.4 MB→40KB + 17KB | 长对话稳态 |

**无论缓存是空是满，文本形态的上行体积都小于原始 JSON。**

## 范围：只做 Chat Completions

**本期只实现 OpenAI Chat Completions 的 Renderer / Unrenderer。**

理由：

- 转换器只支持这一种格式，先把它做对
- 传输层与缓存层在设计上与具体协议无关，后续增加 Messages / Responses 只是新增一组 Renderer，不动核心

**明确不做的：**

- ❌ Anthropic Messages API 转换
- ❌ OpenAI Responses API 转换
- ❌ 多模型族的模板适配
- ❌ 直接对接推理引擎的 token / KV cache 接口
- ❌ 跨模型族的中间格式（harmony 等）

## 需要移除的现有能力

| 现有 | 处理 |
|---|---|
| `X-Cache-Hash` / `X-Cache-Prefix-Length` 协议头 | 移除（改用帧流） |
| `412` fast_fail + 客户端重试 | 移除（改为退化直传） |
| `segment.split()` 回合切分 | 移除（改为 CDC 字节分块） |
| `merkle.chain_hash()` 链式哈希 | 移除（改为内容寻址） |
| `sys` / `tools` 独立缓存段 | 移除（文本里没有这个概念） |
| `pfx` 链节点与访问驱动续期 | 移除（无链） |
| `meta` 入口与 TTL | 移除（无入口概念） |
| `openai_patch` 的 monkey patch 方式 | 重写（需要接管 body 编码而非只加头） |

## 待决策

1. **渲染文本格式**：是否与上游模型真实模板完全一致？
   - 一致：上游可直接消费，省一次反渲染；但要求模板与模型严格匹配
   - 自定义：更易双向解析；但网关必须反渲染回 JSON
2. **模板版本策略**：`block_id` 是否加模板版本前缀？
   - 加：版本切换不会静默错配；跨版本不能复用
   - 不加：跨版本可复用；但模板改动会造成全部 miss
3. **客户端本地保存什么**：只存「已知 block_id 集合」，还是也存块内容？
   - 只存 id：省内存；但客户端无法独立重建完整请求
   - 存内容：支持离线降级为本机重建

## 验收标准

- [ ] 同一 messages 渲染两次，文本逐字节相同
- [ ] 任意位置插入 / 删除 / 修改文本后，本地 CDC 块列表中未受影响的块 `block_id` 不变
- [ ] 缓存全空时，请求正常完成，上行体积 < 原始 JSON
- [ ] 命中率 90% 时，上行体积 < 原始 JSON 的 15%
- [ ] 存储不可用时，请求正常完成（退化直传）
- [ ] 网关侧内存占用与请求体大小无关（流式，不构造完整对象）
- [ ] 渲染模板变更后，旧缓存自然 miss 而非产生错误结果
