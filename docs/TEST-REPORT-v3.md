## 4. 存储:一块一个 key(parent‖正文),只有 Redis

生产只有一个存储后端。value 是纯 STRING:`blk:{hash} → parent_hex(32 B) ‖ 正文`。
读一次 = **一个 Lua 脚本走完整条链(1 往返、原子、顺带逐块续 TTL)**,正文里的父哈希
在 Python 侧用 `memoryview` 切掉(零拷贝,不拷正文):

| 操作(829 KB / 512 B 块 = 1,774 块) | 往返 | 耗时(wall) |
|---|---|---|
| 写整串(单脚本,1 key/块) | 1 | 6.7~7.2 ms |
| **读整条前缀**(单脚本 1,774 跳,读 + 续期) | **1** | **5.0~5.6 ms** |

`MemoryChainStore` 只是测试替身(进程内字典),不参与部署,读一次 0.11 ms。

走链是每块一次 `GET` 加一次 `EXPIRE`,单 key 操作成本(脚本内 1,774 次)实测:
`GET` 1.7 ms、`EXPIRE` 约 1.3 ms。**所以「每块一次调用」是这条曲线的分母**,
块大小直接决定单实例上限。

对照过两种切法(同一份 829 KB、8 轮交替):在 Lua 里 `string.sub` 切正文 6.2~6.6 ms,
Python 侧 `memoryview` 切 5.0~5.6 ms——**慢 16%,块越大差距越大(4 KB 时 30%)**,
因为 Lua 的 `string.sub` 是每块一次真实拷贝。

### 4.1 块大小是唯一的旋钮(829 KB 前缀,生产路径实测)

| 块大小 | 块数 | 写整串(1 key/块) | 读一次 | 单实例上限 |
|---|---|---|---|---|
| 512 B | 1,774 | 6.7~7.2 ms | **5.0~5.6 ms** | **~180~200 req/s** |
| 2 KB | 443 | 3.1~4.6 ms | **3.1~3.3 ms** | **~300~325 req/s** |
| 4 KB | 221 | 3.4~3.6 ms | **2.5 ms** | **~395~400 req/s** |
| 8 KB | 110 | 3.2~3.4 ms | **2.2 ms** | **~448~450 req/s** |

块放大只损失「热请求每轮重发不满一块的尾巴」(512 B 时平均 256 B,占 829 KB 的 0.03%)。

### 4.2 高 QPS 怎么凑

```
所需 Redis 实例数 ≈ 峰值 req/s ÷ 单实例上限   (按会话键分片,线性)
```

按 829 KB 上下文、峰值 1,000 req/s 折算:

| 块大小 | 单实例上限 | 需要实例 |
|---|---|---|
| 512 B | ~190 req/s | **~6 个** |
| 4 KB | ~400 req/s | **~3 个** |

同一场景下更大的开销在**网关解码**:19.69 ms/请求 → 约 **50 req/s/核**,
1,000 req/s 约 20 核。存储是独立的一层,两者都要按容量规划。

| 轮次 | 原始 JSON | 上行 | 占比 | 命中率 |

## 7. 正常行为、记录项与真正的代价

### 7.1 看着像代价,其实是正常行为

| 行为 | 为什么不是缺陷 |
|---|---|
| compact / 改中间消息 / 改顶层参数那一轮全文重发一次 | **前缀本身变了**。客户端只持有 `(L, tip)`、没有中间块摘要,无法证明旧前缀仍一致,只能重传。Agent 本来就会频繁 compact / 改消息 / 改参数(v3 里这些都是常规路径),实测一次完整上行为 **280 KB**,传完当轮立即恢复增量。 |

这是「客户端状态 O(1)」的对称面:不存中间摘要,就必须在**前缀变更那一次**付一次全量。
要消掉它只有两条路,都比现状贵:客户端保存前缀中间摘要(回到 v2 的 210 KB/会话),
或让网关在响应头下发检查点(每请求多几百字节)。

### 7.2 记录项(关系不大,先记着)

| 项 | 量 | 说明 |
|---|---|---|
| 客户端一次 `json.loads` | **0.17 ms** / 242 KB,常驻 0.25 MB、峰值 0.75 MB | 要渲染成文本就必须解析 JSON,属接入点固有;相对 25 ms 的端到端,占比 <1% |

### 7.3 真正有意接受的代价

| 代价 | 量 |
|---|---|
| 网关 CPU 与上下文线性 | 888 KB ≈ 20 ms(约 45 MB/s/核) |
| 走链吞吐 | 每块一次 `GET`+一次 `EXPIRE`,所以块大小决定上限:829 KB 全量前缀 512 B 块 ≈ 180~200 req/s、4 KB ≈ 395~400、8 KB ≈ 448~450;实例数 = 峰值 req/s ÷ 单实例上限(1,000 req/s @512 B ≈ 6 个、@4 KB ≈ 3 个) |
| 部署 | 网关从转发代理变成有状态缓存层:要 Redis、要 TTL、要按会话分片 |

## 8. 测量口径

- 吞吐/CPU 表用 `time.process_time()`(CPU 时间),计时区间关 GC,取 7 次最小值;
  端到端用 wall clock(用户感受到的等待)。
- 本次运行机器较空闲:同一份 829 KB 解码 CPU 18.8 ms / wall 18.8~19.3 ms(≈1.0×)。
  历史上 load ≈ 55 时是 CPU 20.4 ms 对 wall 27~471 ms——所以两种口径分开报,
  对机器敏感的行给区间。
- 所有体积数字是**实际线上字节**(请求体 + 头),不是估算。
