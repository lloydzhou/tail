## 4. 存储层次(读一条 829 KB 前缀 = 1,774 块)

| 层次 | 单次读 | 单实例上限 |
|---|---|---|
| `MemoryChainStore`(进程内) | 0.14 ms | 7,092 req/s |
| `CachedChainStore` L1 命中 | **0.11 ms** | **8,929 req/s** |
| `RedisChainStore`(Lua 走链 + MGET) | **7.27 ms** | **≈138 req/s** |

Redis 侧拆开看(1,774 块,wall,15 次最小值):

| 操作 | 往返 | 耗时 |
|---|---|---|
| 写整条链(单脚本) | 1 | 6.64 ms |
| 走链 1,774 跳(单脚本,顺带续 TTL) | 1 | 4.49 ms |
| MGET 1,774 块 | 1 | 2.49 ms |
| **读整条前缀合计** | **2** | **7.27 ms** |

走链是 O(块数):1 块 0.18 ms / 64 块 0.32 ms / 256 块 0.82 ms / 1,774 块 6.25 ms。

**结论**:10 万在线、30 秒一轮的 3,333 req/s,只靠单个 Redis 差 **25~40 倍**;热会话必须命中 L1。

## 5. 端到端(`tools/e2e_bench.py`,真实 uvicorn + 限速上行)

回环(同一份上下文重复提交):

| 请求体 | 原生透传 | Tail(热) | 倍数 | Tail 状态 |
|---|---|---|---|---|
| 66 KB | 1.2 ms | 3.3 ms | 2.7× | hit 0.998 |
| 242 KB | 1.8 ms | 8.5 ms | 4.6× | hit 1.000 |
| 418 KB | 2.2 ms | 12.1 ms | 5.4× | hit 0.999 |
| 888 KB | 3.7 ms | 24.8 ms | 6.7× | hit 1.000 |

回环没有带宽瓶颈,所以 Tail 更慢(它要多做解码/反渲染/重建 JSON)。真实收益:

| 上行带宽 | 原生透传 | Tail(热) | 提速 |
|---|---|---|---|
| 10 Mbps | 740 ms | **25 ms** | **30.0×** |
| 5 Mbps | 1,468 ms | **24 ms** | **60.7×** |
| 2 Mbps | 3,650 ms | **23 ms** | **155.4×** |

多轮对话(5 Mbps,从 888 KB 上下文起,每轮追加一条提问):

| 轮次 | 原生 JSON | 透传 | Tail | 提速 |
|---|---|---|---|---|
| 1 | 909,773 B | 1,472 ms | 33 ms | **45.2×** |
| 2 | 910,214 B | 1,473 ms | 26 ms | **56.6×** |
| 3 | 910,655 B | 1,470 ms | 26 ms | **56.2×** |
| 4 | 911,096 B | 1,472 ms | 26 ms | **55.8×** |
| 5 | 911,537 B | 1,475 ms | 27 ms | **55.0×** |
| 6 | 911,978 B | 1,476 ms | 26 ms | **55.9×** |
| 7 | 912,419 B | 1,476 ms | 26 ms | **56.1×** |
| 8 | 912,860 B | 1,477 ms | 25 ms | **57.9×** |

透传耗时 = 888 KB / 5 Mbps 的物理下限;Tail 只剩「新增提问 + 网关解码整条前缀」的固定成本。

真实对话周期(200 KB → 800 KB → compact → 200 KB):

| 轮次 | 原始 JSON | 上行 | 占比 | 命中率 |
|---|---|---|---|---|
| 起点 ~200 KB(冷) | 286,073 | 285,888 | 99.9% | 0.0% |
| 增长中 ~455 KB | 466,262 | 180,267 | 38.7% | 61.3% |
| 增长中 ~690 KB | 706,514 | 240,143 | 34.0% | 66.0% |
| 涨到 ~807 KB | 826,640 | 120,065 | 14.5% | 85.5% |
| **compact 之后** | 280,008 | 279,918 | 100.0% | 0.0% |
| compact 后 +1 轮 | 340,071 | 60,391 | 17.8% | 82.2% |
| compact 后 +2 轮 | 400,134 | 60,512 | 15.1% | 84.9% |

compact 那一轮**必然全量重发**:客户端只有 `(L, tip)`,没有中间块摘要,证不出旧前缀仍然一致。

## 6. 与 v2 对照

| 指标 | v2 | v3 |
|---|---|---|
| 块哈希由谁算 | 客户端(服务端只能信) | **只在网关** |
| 829 KB 全命中上行 | 30,158 B | **315 B** |
| 线上固定开销 | 上下文 3.3% | **≈ 0** |
| 客户端每会话状态 | 131 B/块,210 KB | **24 B** |
| compact 那一轮 | 部分失效(tools+system 仍命中) | **全量重发**(客户端状态 O(1) 的代价) |
| 投毒风险 | 存在 | **结构上不可能** |
| 网关每请求 CPU(888 KB) | 只解码 | ~20 ms(切块+哈希+走链+重建) |

## 7. 已知代价(有意接受)

| 代价 | 量 |
|---|---|
| compact / 改中间消息 / 改参数 → 全文重发 | 一次完整上传(实测 280 KB) |
| 客户端一次 `json.loads` | 0.17 ms / 242 KB,峰值 3× 内存 |
| 网关 CPU 与上下文线性 | 888 KB ≈ 20 ms |
| 走链吞吐 | Redis 单实例 ~138 req/s(全量前缀),必须靠 L1(8,929 req/s) |
| 部署 | 网关从转发代理变成有状态缓存层:要 Redis、要 TTL、要 L1 容量规划 |

## 8. 测量口径

- 吞吐/CPU 表用 `time.process_time()`(CPU 时间),计时区间关 GC,取 7 次最小值;
  端到端用 wall clock(用户感受到的等待)。
- 本次运行机器较空闲:同一份 829 KB 解码 CPU 18.8 ms / wall 18.8~19.3 ms(≈1.0×)。
  历史上 load ≈ 55 时是 CPU 20.4 ms 对 wall 27~471 ms——所以两种口径分开报,
  对机器敏感的行给区间。
- 所有体积数字是**实际线上字节**(请求体 + 头),不是估算。
