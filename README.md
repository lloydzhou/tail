# Tail —— 给 LLM 请求做 tail -f

> *Send the tail, the head is cached.*

日志没人每次都 `cat` 全文，只盯新增的那几行。**Tail 对 LLM 请求做同一件事**：
前缀在网关里已经有了，客户端只发增量。

实现上它是一层「文本去重传输层」，插在 SDK 和上游网关之间。客户端把每轮重复的
`messages` 前缀换成**请求头里的一个凭据**，请求体只剩新增的那一小段。
**热请求上行省 99%，5 Mbps 链路上 TTFT 快 55~60 倍**，而上游收到的 prompt 与原来逐字节相同。

那既然缓存命中率已经 99%+，为什么我每一轮还要把重复的东西全部传一遍？

## 为什么值得做

缓存省掉的是**上游的算力**，省不掉我的**上行带宽**和**等待时间**：SDK 每一轮
仍然把完整 `messages` 序列化、打包、上传一次。重复的东西，公网上再走一遍。

所以网关这一跳值得优化。注意收益落在**两拨人**身上，不要混为一谈：
**用户省时间，服务商省容量（或钱）。** 节省 TTFT 就是在珍惜生命。

### 对用户：省的是时间，不是钱

要说清楚：**那点上行流量对用户根本不是成本**。800 KB × 20 轮 = 16 MB，按公网价
也就一分多钱，没人会为这个换方案。

用户真正有感的只有一件事：**每次请求要等多久**。而请求「发完」是 TTFT 的前置段——
链路上行越窄，这段等待越明显。限速模拟公网实测：

| 上行带宽 | 原生 | Tail | 每轮省下 |
|---|---|---|---|
| 10 Mbps | 740 ms | **25 ms** | 0.72 s |
| 5 Mbps | 1,468 ms | **24 ms** | 1.44 s |
| 2 Mbps | 3,650 ms | **23 ms** | 3.63 s |

把「每轮」换成实际强度看（888 KB 上下文、250 工作日/年；上下文小则按比例缩）：

| 使用强度 | 10 Mbps 省下 | 2 Mbps（移动网络、跨境链路）省下 |
|---|---|---|
| 200 轮/天（轻量对话） | 2.4 分钟/天 → **10 小时/年** | 12 分钟/天 → **50 小时/年** |
| **2,000 轮/天**（agent 常态：一次 turn 就要打几十次工具调用） | 24 分钟/天 → **100 小时/年** | 2.0 小时/天 → **504 小时/年** |
| 5,000 轮/天（多个会话并行） | 1.0 小时/天 → 250 小时/年 | 5.0 小时/天 → **1,260 小时/年** |

按 **turn** 看更直观：一次 agent turn 打 50 次请求，2 Mbps 下原生光上传就要等 **3 分钟**；
Tail 下约 **1.4 s**（50 × 28 ms）。长 turn 打 200 次请求就是 12 分钟 vs 5.6 s。

并行会话是**共享同一条上行**的，原生在带宽上互相排队：10 Mbps 下开 4 路，每路每轮从
0.74 s 涨到 **2.96 s**；Tail 每路只发 315 B~2 KB，你的链路上几乎没有排队，每轮仍是
30 ms 量级（它的瓶颈在网关 CPU——按 50 req/s/核 扩容，不在你的宽带上）。

口径说明：上面是按「每轮等待累加」算的。多会话并行时你并不会逐轮盯着，**墙钟体感会小
于这个和**；但并行恰恰是原生更吃亏的地方（共享上行排队），而 Tail 的开销不随并行路数涨。

**上行少两个数量级，等待就少一个数量级。** 这是 Tail 对用户的全部价值。

**这笔账要分成两本，别混着算：个人时间账（独占一条上行）和供应商容量账（共享链路）。**

#### 时间账：个人、独占这条上行时，一轮等多久

只有「请求发完」的时间进入个人体感，所以判据是一条不等式：

```
省下的上行时间((S − 尾巴字节) ÷ 有效带宽)  >  Tail 侧开销
```

Tail 侧开销**不是常数**（同一台机器实测，512 B 块）：

| 上下文 | 满块 | 客户端 prepare | 网关解码 + 重建 JSON | Redis 读整条前缀 | 合计 |
|---|---|---|---|---|---|
| 66 KB | 132 | 0.2 ms | 1.5 ms | 0.5 ms | **≈2.2 ms** |
| 242 KB | 484 | 0.8 ms | 5.3 ms | 1.6 ms | **≈7.7 ms** |
| 418 KB | 836 | 1.4 ms | 9.1 ms | 2.5 ms | **≈13.0 ms** |
| 888 KB | 1,774 | 3.0 ms | 19.7 ms | 5.3 ms | **≈28.0 ms** |

再加一项**随带宽变**的尾巴上传（315 B ~ 2 KB ÷ 带宽：5 Mbps 时 0.5~3.3 ms，
100 Mbps 时 0.03~0.16 ms）。以 888 KB 上下文、合计 ≈28 ms 为例：

| 有效上行 | 原生上传 888 KB | 尾巴上传(315 B / 2 KB) | Tail 合计(315 B / 2 KB) | 净收益(315 B / 2 KB) |
|---|---|---|---|---|
| **5 Mbps**（实测 1.5 s 上传即此量级） | 1,456 ms | 0.50 / 3.28 ms | 28.5 / 31.3 ms | **省 1.43 s（51×）/ 1.42 s（47×）** |
| 10 Mbps | 728 ms | 0.25 / 1.64 ms | 28.3 / 29.6 ms | 省 0.70 s（26× / 25×） |
| 50 Mbps | 146 ms | 0.05 / 0.33 ms | 28.1 / 28.3 ms | 省 118 ms（5.2×） |
| 100 Mbps | 73 ms | 0.03 / 0.16 ms | 28.0 / 28.2 ms | 省 45 ms（2.6×） |
| 200 Mbps | 36 ms | 0.01 / 0.08 ms | 28.0 / 28.1 ms | 省 8 ms（1.3×） |
| **≈260 Mbps（盈亏平衡）** | 28 ms | ≈0 | 28.0 ms | 打平 |
| 1 Gbps | 7 ms | 0.00 / 0.02 ms | 28.0 ms | 亏 21 ms |

跨 200 倍带宽，原生从 7 ms 涨到 1,456 ms（200×），Tail 合计从 28.0 到 31.3 ms（1.12×）：
**开销从「带宽的函数」变成「上下文长度的函数」**——上下文短，开销跟着小（66 KB 只有
2 ms 量级）；上下文长，开销变大但仍与带宽脱钩。

注意这张表的前提是「一个人独占这条上行」。而且这个账**不对称**：过了盈亏平衡点，时间
最多也就亏掉一整个开销（≈28 ms，上限固定）；低于它时，收益随带宽下降**没有上限**
（2 Mbps 时省 3.65 s）。所以时间账的最坏情况是「多等 28 ms」，最好情况是「少等几秒」。

注意「有效带宽」要按真实链路算：888 KB 在公网上要几十个 RTT 才传完（TCP 慢启动 +
拥塞控制），实测 1.5 s 的上传对应的**理论**带宽只有 ~4.9 Mbps。所以哪怕用户签的是
百兆宽带，单次 888 KB 上传的有效速率也常常落在盈亏平衡点以下——收益不是给机房内网
准备的，是给真实公网准备的。

两点口径说明：① 5.3 ms 的 Redis 读是分项实测的最小值，中位 5.4 ms、偶发 7~8.5 ms
尖峰（宿主机负载）；② 分项相加 ≈28 ms 是**上界**，限速端到端实测是 24~25 ms
（Redis 读与尾包上传、网关解码有部分重叠），所以用 28 ms 算盈亏平衡偏保守。

冷启动那一轮多付一次整链写入（829 KB ≈ 7 ms）；compact / 改中间消息那一轮是
「原生上传 + 28 ms」。两者都是单次事件，不改变上面的结论。

**这只是「你自己等多久」的账**：过了盈亏平衡点最多亏掉一整个开销（≈28 ms，上限固定），
没过点时收益没有上限（2 Mbps 省 3.65 s）。而供应商那本容量账跟链路快慢无关——字节削减
400×~2,900× 是恒定的，**没有盈亏平衡点**，见下一节。

### 对服务提供商：同样的带宽，能多撑两个数量级的人

带宽成本落在**服务提供方**这一侧——入口流量、跨区链路、带宽峰值容量，
都是按 GB 和带宽峰值计费的。

**先明确「一轮」是什么**：上行（把这轮的 messages 传上去）→ 推理（到首 token）→
流式回传 → 可能的工具调用 → 下一轮。所以同一个会话相邻两次请求的间隔 **T**
不是「思考 10 秒」，是**整个轮周期**，通常 20~60 秒，带工具调用会更长。
上行只占其中一小段，但它**卡在关键路径最前面**：prefill 必须等 body 收完才能开始。

于是每个会话的请求速率 = 1/T，入口的平均上行 = **同时在线会话数 × 单轮体积 / T**。
关键差别在于「单轮体积」：

- 原生 SDK：每轮把**整个上下文**（800 KB）推上去。
- Tail：每轮只推**这一轮新增的内容**——纯对话约 2 KB，带工具结果约 10 KB。

按每 **1,000 req/s** 折算（对应多少在线会话取决于轮周期 T：在线数 ≈ 1,000 × T），量级很直观：

| 指标 | 原生 SDK（800 KB/轮） | Tail（2 KB/轮） | Tail（10 KB/轮） |
|---|---|---|---|
| 平均上行 | **6.4 Gbps** | **16 Mbps** | 80 Mbps |
| 上行流量 | 69 TB/天 | 0.17 TB/天 | 0.86 TB/天 |
| 1 Gbps 出口能扛 | 156 req/s | 62,000 req/s | 12,500 req/s |

**比值约 400 倍（纯对话）到 80 倍（带工具结果）**（同前缀全命中时是 2,900 倍），而且上下文越长这个倍数越大——
原生上行随上下文线性涨，Tail 的上行只跟「每轮新增」有关。把 1,000 req/s 放大到你们的
实际量级，原生那一列会直接变成「几十个 100G 口、跨区专线和运营商带宽包」的账，而且得
按峰值签；Tail 那一列还在一个 1G 口的量级内。

**这本账没有盈亏平衡点**：削减倍数只取决于「每轮新增多少字节」，与你给我的链路多快无关。
所以「带宽很好、所以不值得」只在**个人时间账 + 独占带宽 + 888 KB 上下文**这个很窄的条件下
成立，而且时间上最坏也只亏 ≈28 ms。

存储不是对价：块只存每轮真正的新内容（纯对话约 2 KB/轮，带工具结果约 10 KB/轮），
每 1,000 req/s 每天约 0.17~0.86 TB，配 3 天 TTL 后占用 **0.5~2.6 TB**，
ESSD 约 **¥250 ~ ¥1,300/月**。存储会随 TTL 自动回收，上行流量不会。

**一个诚实的推论**：瓶颈会**从带宽转到网关 CPU**。上行省 400 倍之后，网关要多做
「切块、父链哈希、走链取块、反渲染、重建 JSON」——按实测 888 KB 上下文约 **20 ms CPU**
（`tools/bench.py`），也就是**每核约 50 req/s**，每 1,000 req/s 就要 ~20 核；
上下文均值按 400 KB 算是 ~10 核。这比推理集群小，但已经不是零：它意味着网关要按
「CPU 密集服务」来扩容，而不是「转发代理」。按会话键分片 Redis 是标配，
实例数 = 峰值 req/s ÷ 单实例上限（见「存储」一节）。

**所以这是个双边收益的东西**：用户拿走时间，服务商拿走容量（或成本）。
任何一方单独看，都不足以支撑这个复杂度；两边加起来才成立。

### 代价（诚实版）

| 项 | 量 |
|---|---|
| 客户端额外 CPU | 0.8 ms / 242 KB 请求（热路径要重算整条前缀的父链哈希做自检） |
| 网关解码 CPU | 20 ms / 888 KB 上下文（线性，约 45 MB/s/核） |
| 固定引用开销 | **≈ 0**：线上没有逐块帧头，热请求只剩不满一块的尾巴（≤511 B） |
| 前缀变更（正常行为，不算代价） | compact / 改中间消息 / 改参数那一轮全文重发一次（实测 280 KB）；agent 本来就常做这些，传完当轮立即恢复增量 |
| 回环上反而更慢 | 25 ms vs 3.7 ms —— 回环没有带宽瓶颈，收益只在真实链路上出现 |
| 部署复杂度 | 网关从「转发代理」变成「有状态缓存层」：要 Redis、要 TTL、要按会话分片 |

## 它解决什么问题

一个 100 轮、每轮 1K token 的对话，到第 100 轮时请求体约 400KB，其中 99% 是前 99 轮
已经传过的内容。Tail 把这部分换成了请求头里的一个凭据：`X-Tail-Have: 359424;<16 字节哈希>`。

实测（20 轮中文对话，每轮追加一轮问答，`tools/bench.py`）：

| 口径 | 数 |
|---|---|
| 后 10 轮平均上行 | **880 B** |
| 同一上下文冷启动 | 10,198 B |
| 末轮上行 / 上下文长度 | 858 B / 12,610 B（6.8%） |

关键性质：**上下文线性增长，线上体积基本持平。** 38 KB 的上下文热请求只剩 **374 B**、
908 KB 的只剩 **315 B**——都是「不满一个 512 B 块」的那截尾巴。

## 怎么做的

```
客户端                                          网关
──────────────────────────────────────────────────────────────
messages JSON
  │ ① 渲染器（懂 LLM 语义，确定性）
  ▼
一维文本流
  │ ② 前缀自检：边渲染边算父链哈希，走到已知 (L, H) 就停
  ▼
X-Tail-Have: L;H  +  body = 文本第 L 字节之后的部分
────────────────── 公网（只剩这一段）──────────────────→
                                            │ ③ 切块 + 父链哈希（**唯一权威**）
                                            │ ④ 按 (L,H) 从 Redis 走链取前缀，
                                            │    新块连同父链一次原子写回
                                            ▼
                                       一维文本流
                                            │ ⑤ 反渲染器（懂 LLM 语义）
                                            ▼
                                       messages JSON → 上游推理 API
```

职责单一，可独立替换：

| 层 | 模块 | 输入 → 输出 | 懂 LLM 语义？ |
|---|---|---|---|
| 渲染器 | `render.py` | messages JSON → 一维文本 | ✅ |
| 前缀客户端 | `codec.PrefixClient` | 文本 + 凭据 → 尾部字节 | ❌ |
| 前缀读取器 | `codec.PrefixReader` | 前缀 + 尾部字节 → 完整文本（**在这里切块、算哈希**） | ❌ |
| 反渲染器 | `render.py` | 一维文本 → messages JSON | ✅ |
| 分块与哈希 | `chunking.py` | 字节流 → (块哈希, 块) | ❌ |
| 链式存储 | `storage.py` | 链尾 + 块数 → 块列表 / 块内容 | ❌ |

**中间几层完全不知道聊天协议。** 要支持 Anthropic Messages 或 Responses API，
只需写一个新的 `render` 模块，其余一行都不用改。

## 三条不变式

1. **渲染必须确定性** —— 同一份 messages 必须渲染成逐字节相同的文本，否则
   块内容变化、`block_hash` 变化、缓存整体失效。实现上：字段顺序固定、
   `json.dumps(sort_keys=True)`。格式版本走 HTTP 头，不写进正文。
2. **哈希只在网关算** —— 客户端一个哈希都不发，只发「我认为你已经有哪些」（`L;H`）。
   网关自己切块、自己算父链、自己写存储。所以「客户端投毒污染别人的块」在结构上
   不可能发生：客户端发错最多落在一棵无关的链上，等价于 miss。
3. **缓存缺失只退化，不报错** —— 前缀不完整时网关立刻中断上游请求、回 409 +
   `X-Tail-Retransmit: 1`，客户端丢掉凭据重发全文一次，对调用方透明。

## 为什么不用原 JSON 直接传

**完整协议、管线与设计动机见 [`docs/TRANSPORT-PIPELINE.md`](docs/TRANSPORT-PIPELINE.md)。**

要点：

- **JSON 是树，块边界没有自然落点。** 渲染成固定格式文本后是一维字节流，
  块边界按固定 `block_size` 对齐即可（vLLM 的做法）。
- **前缀缓存消不掉新增消息里的结构字节。** 每条新消息都带 `{"role":"`, `","content":"`
  这些零信息开销。不过要诚实：正文很长的对话里这只占个位数百分比（实测长对话
  40,141 B → 38,262 B，只省 4.7%）。**渲染的真正价值是把树摊平成一维字节流，
  让块能按固定间隔切、跨轮复用**，不是省那点标点。
- **尾部增量只能处理追加。** compact、编辑旧消息、重排、中间插入都会导致整条前缀
  失效；分块去重下只重传受影响的块。

## 快速开始

```bash
pip install -e ".[test]"

# 起网关（不填 --redis 就用进程内存储，重启即丢，只适合开发）
docker run -d --rm -p 6379:6379 redis:7-alpine
python -m tail.serve --backend https://api.deepseek.com --port 8765 \
    --redis redis://127.0.0.1:6379/0 --ttl 1800
```

客户端：**现有的 `openai` 代码不用改请求逻辑**，只多传一个 `http_client`。

```python
import httpx2
from openai import OpenAI
from tail.transport.client import TailTransport

client = OpenAI(
    base_url="http://127.0.0.1:8765/v1",
    api_key="sk-xxx",
    http_client=httpx2.Client(transport=TailTransport()),   # ← 唯一新增
)

# 下面和原生用法一模一样，流式也一样
for event in client.chat.completions.create(
        model="deepseek-chat", messages=messages, stream=True):
    print(event.choices[0].delta.content or "", end="")
```

异步用 `AsyncOpenAI` + `httpx2.AsyncClient(transport=TailAsyncTransport())`。

### 客户端只记凭据，不缓存内容

本地状态是「会话键 → 若干 `(L, H)` 凭据」，每条 **24 字节**（8 B 长度 + 16 B 哈希），
每会话最多留 4 条（MRU，容忍并发乱序的响应）。**不留正文副本，也不留块哈希表。**

实测（800 KB 上下文，1,774 个满块）：

| | |
| --- | --- |
| 客户端本地状态 | **96 B**（30 轮会话，4 条凭据封顶） |
| 冷启动上行 | 908,603 B（就是渲染文本本身；同体积 JSON 是 909,206 B） |
| 全命中后上行 | **315 B**（只剩不满一块的尾巴：908,603 mod 512） |
| 每轮新增一条提问时上行 | 约 0.4~1 KB（就是那条新提问） |

三点要注意：

1. **必须复用同一个 client 实例**——凭据挂在 transport 上，每轮新建 `OpenAI(...)`
   等于永远冷启动（6 轮合计 14,109 B vs 5,405 B，差 62%）。
2. **复用是前缀形状的**——块哈希沿用 vLLM 的父链 `hash(parent, block)`，纯追加几乎
   免费；但要**客户端能证明**旧前缀没变：它只持有 `(L, H)` 而没有中间块摘要。
   所以前缀本身一变（compact、改中间消息、改顶层参数）这一轮就全文重发一次
   （实测 280 KB）——这是**正常行为**，agent 本来就会频繁做这些，传完当轮立刻恢复增量。
3. **服务端是权威**——`X-Tail-Have` 是「我认为你有」，不是「你必须信」。网关按
   `(L, H)` 走链，走不通就回 409 让客户端重发。客户端不会因为猜错而拼出错误前缀。

`TailTransport` 只拦截 `/chat/completions` 的 JSON 请求，其余请求（`/models`、
embeddings、文件上传……）原样透传；网关回 `X-Tail-Retransmit` 时它自动丢掉该会话
凭据并重发一次全量，对上层透明。

完整可运行示例见 [examples/chat.py](examples/chat.py)（原生）与
[examples/chat_tail.py](examples/chat_tail.py)（接入 Tail），两者 diff 只有 3 行。

网关也接受普通 `application/json` 请求并原样转发，便于灰度对比与排障。

### 依赖说明：为什么是 `httpx2`

`httpx` 稳定版停在 0.28.1（后续只有 `1.0.dev*` 预发布），继任包是
[`pydantic/httpx2`](https://github.com/pydantic/httpx2)（同一作者 Tom Christie）。
`openai` 3.x 已依赖 `httpx2`，Starlette 1.10 的 `TestClient` 也优先用 `httpx2`
并对 `httpx` 报弃用警告。所以本项目统一用 `httpx2`，客户端与网关只有一套 HTTP 栈。

`TailTransport` 本身与库无关：它按请求对象所属的库自动选择内层 transport，
因此仍在用 `httpx` 的 `openai` 1.x 也能直接接。

### 直接用底层 API（不用 SDK）

```python
from tail.transport.gateway import TailClient

client = TailClient()
prepared = client.prepare({"model": "deepseek-chat", "messages": messages})
resp = httpx2.post(
    "http://127.0.0.1:8765/v1/chat/completions",
    content=prepared.body,                      # 生成器，边渲染边发
    headers={"content-type": "application/x-tail-v3",
             "x-tail-have": (f"{prepared.have_len};{prepared.have_tip.hex()}"
                             if prepared.have_len else ""),
             "authorization": f"Bearer {api_key}"},
)
client.update_from_headers(prepared.session, resp.headers)   # session 是本地键,不上线
if resp.headers.get("x-tail-retransmit"):
    client.invalidate()                        # 前缀失效，下一轮重发全文
```

### 接 magpie：两个 magpie、各一个开关

magpie（Go，本地一个 + 集群一个）里这套传输是原生实现的，不需要旁路进程：
`internal/tail` 是协议的 Go 实现（渲染/切块/链/存储，与 Python 版本逐字节对拍），
gateway 的两端各挂一个开关。

**集群侧的 magpie（出站侧的老大：它接受尾巴字节）**

```bash
MAGPIE_TAIL=1 magpie serve         # gateway 开关：接受 application/x-tail-v3
```

这个开关放在环境变量里（和 `MAGPIE_ADDR`、`MAGPIE_ALLOW_IPS` 一样），不进
`settings.json`：它是**某个部署的位置**的属性——「我前面是不是有个会发尾巴的
客户端」——不是本地使用偏好。同一个人的本地 magpie 开着客户端、集群 magpie 开着
服务端，两边都不需要改配置文件。

**本地侧的 magpie（把 provider 指过去，加一个 `tail=on`）**

```bash
magpie provider add peer url=http://10.0.0.5:3425/v1 key=sk-… models=… tail=on
```

provider 的 `url=` 还是普通的 chat completions 地址（`…/v1`），`tail=on` 只改变
「同一个地址怎么发」——所以 A/B 对比就是换一个 provider 名，请求体一模一样。

实测（两个真实 magpie 二进制，中间用计字节的 TCP 中继观测**两个 magpie 之间的
真实线上字节**，mock 推理服务在集群侧，同一个 agent 会话逐轮变长）：

| 轮 | plain 上行 | tail 上行 | 省 |
| ---: | ---: | ---: | ---: |
| 1 | 42.0 KB | 41.9 KB | 1.0x |
| 2 | 52.0 KB | 10.4 KB | 5.0x |
| 4 | 72.0 KB | 10.3 KB | 7.0x |
| 6 | 92.1 KB | 10.7 KB | 8.6x |
| 8 | 112.1 KB | 10.6 KB | 10.6x |
| 10 | 132.0 KB | 10.3 KB | 12.8x |
| 合计 | **0.85 MB** | **0.13 MB** | **6.4x** |

第 1 轮是全量（冷启动），之后每轮只上行「新增的那一轮」；两条路到达推理服务的
messages 逐轮一致（保真校验）。

**但纯追加是最理想的情况。** 真实 agent 还会 compact、回退分支、中途加工具、开多个
会话——这些都会让前缀失效。所以真正取数要走 `tools/realworld.py`：它生成的轨迹里
带这些事件，并且中间那条链路**按真实上行带宽限速**，于是上表里的「字节」直接变成
「时间」。

同一段 20 轮轨迹（2 个会话、40 KB 系统提示、每轮约 24 KB），在 25 Mbps 上行下：

| 事件 | 轮数 | plain 上行 | tail 上行 | plain 上传 | tail 上传 | 省 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| append（纯追加） | 16 | 3.27 MB | 0.69 MB | 1,337 ms | 253 ms | **4.7x** |
| branch（回退分支） | 2 | 0.37 MB | 0.23 MB | 153 ms | 90 ms | 1.7x |
| new_tools（加工具） | 1 | 0.18 MB | 0.18 MB | 73 ms | 74 ms | 1.0x |
| compact（压缩历史） | 1 | 0.12 MB | 0.12 MB | 49 ms | 50 ms | 1.0x |
| **合计** | 20 | **3.85 MB** | **1.18 MB** | **1,612 ms** | **466 ms** | **3.3x** |

这张表最该看的不是 3.3x，而是**最后两行的 1.0x**：compact 和历史重排是**结构上**
无法省的——前缀变了就是变了，只能整传一次。所以：

- 省的是「对话在增长的绝大多数轮」——这也是 agent 的真实形态（一次 turn 跑半天、
  几十轮工具调用）；
- compact 那几轮的省是**严格 0**，不要把它算进平均收益；
- 带宽越窄，省的绝对时间越多：同一轨迹在 10 Mbps 下，plain 3.95 s / tail 0.90 s
  （省 3.05 s），而且**带宽降 2.5 倍，plain 上传耗时正好涨 2.45 倍**——这交叉验证了
  限速确实在测真实传输时间，不是空转计时。

上下文越大，这个差越明显：另一段 12 轮轨迹从 177 KB 长到 505 KB，25 Mbps 下

| 轮 | 事件 | JSON | plain 上传 | tail 上传 |
| ---: | --- | ---: | ---: | ---: |
| 1 | append | 177.8 KB | 73.6 ms | 73.1 ms |
| 4 | append | 341.0 KB | 138.5 ms | 20.0 ms |
| 6 | append | 450.2 KB | 186.3 ms | 20.2 ms |
| 7 | compact | 233.3 KB | 96.8 ms | 96.7 ms |
| 12 | append | 505.8 KB | 208.2 ms | 20.0 ms |

**plain 的上传耗时随上下文线性增长，tail 的基本是一条水平线**——因为它每轮只上行
「新增的那一轮」（约 55 KB），与上下文多长无关。这就是「一次 turn 跑半天」的 agent
为什么受益最大：上下文越长，每轮重传的浪费越多。

### 不理想的条件：并发、乱序、网关重启

上面的数据都是单线程串行发的。真实 agent 不长这样：同时开几个会话，请求交错甚至
并行；网关也会重启（升级、崩、被调度器挪走）。这三件事都可能让**数据失真**或
**功能悄悄退化**。

**这些不变量是 magpie 实现的性质，所以断言写在 magpie 里**（`go test` 就能跑，
不需要 Python，也不需要起两个进程）：

```bash
cd magpie
go test -run 'TestTailParallelSessionsDoNotMix|TestTailRecoversAfterTheFarEndStartsWithNothing' ./internal/gateway/
go test -run 'TestOutOfOrderRepliesKeepTheLongestPrefix' ./internal/tail/
```

下面的数字是**同几件事在两个真实进程、真实线上字节下**量出来的 —— 由
`tools/hardcases.py` 产出（Go 测试证明不变量成立，这个工具量化代价）：

| 场景 | 断言 | 实测 |
| --- | --- | --- |
| 4 个会话 × 3 轮全部并行 | 推理服务收到的每条 messages 都必须**恰好等于某个会话某一轮的完整历史**（不串台） | 12/12 条正确，串台 0，错误 0 |
| 同一会话 4 个请求同时在飞，且**最早的（历史最短）那个最后回来** | 下一轮仍要复用**最长**那份前缀，而不是被最后到达的短响应覆盖 | 上行 20,495 B / 全量 131,404 B（6.4x）；按最长复用算术值 20,017 B；**只留 1 条凭据会是 80,433 B** |
| 集群 magpie 被杀掉重起（块缓存清空） | 恰好浪费一轮：集群回 409 → 客户端丢凭据全量重发 → 上层 agent 无感；从第二轮回落到「只上行尾巴」 | 第 1 轮 106,475 B（= 白花的 15,766 B 尾巴 + 90,709 B 全量重发），第 2–4 轮 15.6–15.9 KB（全量 106–136 KB） |

第二行是**凭据表要留多条**（`maxCredentials=4`）的理由：只留 1 条时功能完全正常、
仍然有命中、仍然省，只是复用的前缀被后到的旧响应缩回到最短那份。把 `maxCredentials`
改成 1 重跑，同一个检查立刻报出 80,910 B —— 也就是说这个退化**不会报错，只会把
省下来的字节悄悄吐回去**，在曲线图上也看不出来。

第三行的代价是可以精确算出来的：自愈只花「一次被拒的尾巴 + 一次全量」，之后
恢复如常。也就是说重启不是正确性问题（agent 不会看到 5xx），只是一次性的带宽损失。

## 线上格式

`Content-Type: application/x-tail-v3`。**body 就是渲染文本的一段原始字节**——
没有帧、没有逐块元数据。

```
POST /v1/chat/completions
content-type: application/x-tail-v3
x-tail-have: 46208;9c1e77d3…             可选：我认为你已有前 46,208 B，链尾是 9c1e…

<body>                                   渲染文本第 L 字节之后的全部字节

200 OK
x-tail-version: 3
x-tail-have: 51456;71b0c4ae…             下一轮凭据（服务端是权威）
x-tail-status: hit                       hit / miss / degraded
x-tail-hit: 0.998                        本轮前缀命中率（按字节）
```

前缀失效时回 `409` + `x-tail-retransmit: 1`，客户端丢掉凭据重发全文一次。

为什么没有帧：v2 里每块 17 B 引用帧存在的唯一理由是「切块与哈希在客户端，
网关必须被告知块边界」。把切块与哈希搬到网关之后，这个理由消失了——
全命中的线上体积从 1,774 × 17 B ≈ **30 KB** 降到 **315 B**，
固定开销从「上下文 3.3%」降到 **≈ 0**。

## 分块与块哈希

**完全照搬 vLLM Automatic Prefix Caching**
（[设计文档](https://docs.vllm.ai/en/v0.8.3/_sources/design/v1/prefix_caching.md)），
没有自创算法：

```
block_hash = hash(父块哈希, 本块字节)
```

- **定长块**，块边界只由位置决定，与内容无关。
- **哈希链**：父哈希让相同内容挂在不同前缀下得到不同哈希，这是"前缀"语义的来源。
- **只缓存满块**（vLLM: "We only cache full blocks"），尾块不入存储。

DeepSeek 侧对应的是"按固定 token 间隔落盘"
（[上下文硬盘缓存](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)），
同样是固定间隔。

参数：`BLOCK_SIZE = 512` 字节 / `BLOCK_ID_SIZE = 16` 字节 / blake2b。

**`BLOCK_SIZE` 为什么不是 vLLM 的 16 token（≈48 B）**：块越小，走链跳数越多，
而每次读前缀都要从链尾一跳一跳走到链头。829 KB 上下文按 512 B 切是 **1,774 跳**，
按 48 B 切就是 **17,706 跳**——存储读成本差 10 倍，换来的只是「尾巴少重发 400 字节」。

| block_size | 48 B | 128 B | 256 B | **512 B** | 1024 B | 4096 B |
|---|---|---|---|---|---|---|
| 829 KB 的块数（走链跳数） | 17,706 | 6,640 | 3,320 | **1,774** | 887 | 221 |
| 每轮重发的尾块上限 | 47 B | 127 B | 255 B | **511 B** | 1,023 B | 4,095 B |

512 是在「尾块浪费 ≤ 0.06%」与「走链跳数可控」之间的折中。

哈希用 blake2b 而非 `hash()`：Borg 明确要求块 id 必须是密码学强哈希，
且内置 `hash()` 带进程随机盐，不能跨进程复用缓存。

## 存储：链和内容在同一个 value 里

因为 `block_hash = hash(父哈希, 本块)`，**链尾摘要等价于整条前缀的入口**：

```
blk:{block_hash} → parent(32 B hex) ‖ content(≤ 512 B)

H → block[1773] → parent → block[1772] → ... → block[0] → 链根
```

给定链尾 `H` 和前缀块数，从后往前走就能还原整条前缀，不需要单独的索引 key。
这是 vLLM 的 `block_hash = hash(parent_hash, block)` 原样搬到字节层——
差别只在链放在哪：vLLM 放进程内存的 block table，这里放存储，好让多个网关实例共享。

**一块一个 key，父哈希和正文在同一个 value 里**：

| key | value |
| --- | --- |
| `blk:{块hash}` | 父哈希（16 B，hex 后 32 B）+ 正文（≤块大小） |

读一条前缀 = **一条 Lua 脚本走完整条链**（一次往返、原子）：脚本按跳取 value、取下一跳
的 key、逐块续 TTL，把整条前缀一次带回；正文里的 32 字节父哈希在 Python 侧用
`memoryview` 切掉——零拷贝，真正的一次拷贝只发生在最后的 `b"".join`。

> 不在 Lua 里 `string.sub(v, 33)` 切：那是每块一次真实拷贝，1,774 块时慢 16%、
> 4 KB 块时慢 30%（块越大越亏）。

**为什么不照抄 vLLM 的索引**：vLLM 的推理进程手里有完整 token 序列，可以从第 0 块
**正向重算**整条哈希再逐个查表，所以它的索引只有 `hash → block_id` 一张字典，块本身
不需要父指针。网关按定义看不到前缀（只收 `(L, tip)` + 尾部），只能从链尾**反向**走，
父哈希就必须真的存下来——这 32 B/块是「看不到全文」这个前提的代价，不是冗余。

**读写都是 Lua，保证原子性**：

- **写**：一个脚本写完整串（同一个 TTL）。否则网关只写了一半就把新 tip 告诉客户端，
  对端拿到悬挂的链，表现为「刚发过的前缀立刻 miss」。
- **读**：一个脚本完成「走链 + 逐块续期」，读和续期是同一件事。递归必须在脚本里做：
  每跳依赖上一跳的结果，由网关逐跳发命令就是 N 次网络往返。

存储只有两个实现，生产只有一个后端：

- `RedisChainStore` —— **生产唯一后端**：`blk:` 一个命名空间 + 两个 Lua 脚本
  （写整串 / 走链读整条），读时顺带续 TTL（`pip install redis`）
- `MemoryChainStore` —— 进程内字典，**仅测试替身**（不落盘、不跨进程、不参与部署）

走链是 O(块数)，所以**块大小决定单实例上限**（829 KB 前缀，`tools/bench.py` 实测）：

| 块大小 | 块数 | 写整条(1 key/块) | 读一次 | 单实例上限 |
| --- | --- | --- | --- | --- |
| 512 B | 1,774 | 6.7~7.2 ms | **5.0~5.6 ms** | **180~200 req/s** |
| 2 KB | 443 | 3.1~4.6 ms | **3.1~3.3 ms** | **300~325 req/s** |
| 4 KB | 221 | 3.4~3.6 ms | **2.5 ms** | **395~400 req/s** |
| 8 KB | 110 | 3.2~3.4 ms | **2.2 ms** | **448~450 req/s** |

读数是多次运行的最小值;中位 5.1~6.2 ms,偶发 7~8.5 ms 尖峰(宿主机负载)。表里是三次运行的范围;`tools/bench.py` 可复现。

所以高 QPS 必须**按会话键分片**：

```
所需 Redis 实例数 ≈ 峰值 req/s ÷ 单实例上限(由块大小与上下文长度决定)
```

829 KB 前缀、1,000 req/s 峰值：512 B 块要 **~6 个实例**，4 KB 块 **~3 个**。
块变大的唯一代价是热请求每轮要重发不满一块的尾巴（512 B 时平均 256 B，占 829 KB 的
0.03%）。
